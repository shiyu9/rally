# 仕様原稿の書式

仕様書の正は `docs/spec.html`(本体)と `docs/spec-flow.html`(別紙「処理の流れ」)。同じ原稿から 2 つ同時に出る。**モデルが書くのは中身だけ**で、HTML は 1 バイトも
`scripts/spec_build.py` が持つ。章立て・列構成・記号・配色・目次・検索は原稿によって
ぶれない。目次・件数・判定・図の番号を手で書いてはならない。

```
docs/.spec-src.md（モデルが書く行形式の原稿）
        │  python ${CLAUDE_SKILL_DIR}/scripts/spec_build.py --src docs/.spec-src.md --out docs/spec.html
        ▼
docs/spec.html（本体）・docs/spec-flow.html（別紙: 処理の流れ）
```

書き方は 2 つだけ。**キーと値は `キー: 値`、表の行は `|` 区切り。**

書式に合わない行があるとビルドが止まり、既存の `spec.html` は上書きされない。

## 章立て(固定)

| 章 | 章名 | 原稿に書くか |
|---|---|---|
| 1 | 文書情報 | 書く |
| 2 | 用語定義 | 書く |
| 3 | システム概要 | 書く(3.1 概要 / 3.2 ユースケース) |
| 4 | システム構成 | 書く(4.1 構成要素 / 4.2 モジュール結合図 / 4.3 動作環境) |
| 5 | インターフェース仕様 | 書く(5.1 外部インターフェース一覧 / 5.2 インターフェース詳細) |
| 6 | データ仕様 | 書く |
| 7 | 機能一覧 | **書かない(自動生成)** |
| 8 | 機能仕様 | 書く |
| 9 | エラー仕様 | 書く |
| 10 | 非機能要件 | 書く |
| 11 | 適用範囲外 | 書く |
| 12 | 設計判断 | 書く |
| 13 | 仕様の確定状況 | **書かない(自動生成)** |
| 14 | 未確定事項 | 書く |

第 7 章と第 13 章は、第 8 章の機能仕様と 3.2 の処理の流れ、各章の検証欄から機械的に
作られる。**同じ数字を 2 か所に書く場所は無い。**

章名・節名は固定で、1 文字でも違うとビルドが止まる。節名は特定のシステム形状に
寄せていない(「コマンドライン」ではなく「外部インターフェース一覧」)。CLI でも GUI アプリでも
ライブラリでも、同じ節名で書ける。

## 全体の形

```
題名: mdsite 仕様書
対象: Markdown フォルダを HTML サイトに変換する CLI ツール
生成元: tests/e2e/（26 件）・docs/adr.md（8 件）

## 1 文書情報
@def
文書名: mdsite 仕様書
扱い: 生成物。手で編集しない

## 2 用語定義
@def
メモ: 変換元の Markdown ファイル

## 3 システム概要

### 3.1 概要
@p …
```

先頭の `題名` `対象` `生成元` は必須。章見出しは `## <番号> <章名>`、
節見出しは `### <番号> <節名>`。

## 指示の一覧

| 指示 | 用途 | 中身の書き方 |
|---|---|---|
| `@p` | 段落 | 指示と同じ行に本文 |
| `@def` | 定義表(項目｜内容) | `キー: 値` |
| `@table 列1 \| 列2 …` | 自由列の表 | `値1 \| 値2 …` |
| `@code` … `@end` | コード | そのまま |
| `@io` | 外部インターフェースの図・一覧表と詳細(5.1 / 5.2) | 後述 |
| `@peer` `@if` | 外部エンティティと、1 対の要求と応答(インターフェース) | `@io` の中。後述 |
| `@paths` | インターフェース詳細の差し込み(5.2) | 中身は書かない |
| `@purpose` | 目的(ユースケース)の見出し(3.2) | 指示と同じ行に `P-01 <目的名>` |
| `@flow` | 処理の流れ(3.2 に書き、別紙に出る) | 後述 |
| `@param` `@return` | 要求パラメータと応答項目(5.2) | `@if` の下。後述 |
| `@graph` | モジュール結合図(4.2) | 後述 |
| `@store` | データストア(6) | 指示と同じ行に `<名前> \| <保管場所>` |
| `@schema` | データストアの項目表(6) | 後述 |
| `@dfd` | ユースケースの中の処理を分けたデータフロー図(6) | 指示と同じ行に `P-01`。後述 |
| `@spec` | 機能仕様ブロック(8) | 後述 |
| `@rows` | ID 付き条項表(9〜12・14) | 後述 |
| `@caption` | 直前の図の脚注(記法の説明は書かない。後述) | 指示と同じ行に本文 |

章ごとに使える指示は決まっている。使えない指示を書くとビルドが止まり、その章で
使えるものを教える。

## 文中の記法

- `` `…` `` はコード。`<` `>` `&` は自動でエスケープされるので、そのまま書いてよい
- `**…**` は強調
- `F-01` `E-03` `N-02` `X-04` `D-06` `U-01` は**自動でリンクになる**。手で書かない
- **図の中では装飾が効かない。** 工程名や要素名はそのままの文字として描かれる
  (SVG は HTML のタグを持てない)。機能 ID は `| F-01` で添えるとリンクになる

## 3.1 概要 — このシステムが何を提供し、どんな価値を持つか

読み手が数行で「何のシステムか」をつかめるようにする。**後続の章と重複してよい。**

```
### 3.1 概要
@p kashikari は、人との貸し借りの情報を記録し、貸出状況の可視化と返却忘れの防止を行うコマンドラインツールである。
@p kashikari コマンドにより、貸出情報の登録・一覧表示・訂正・削除と、返却・譲渡の登録、履歴の表示を行うことができる。貸出中一覧では、返却期限を超過した貸出と長期の貸出を先頭に表示する。
@p 通知、スマートフォンからの利用、借りた物の管理は対象外とした。
@p 詳細な範囲は第 11 章、決定の理由は第 12 章に記載する。
```

- 段落の順は **何のシステムか(提供するものと価値) → 提供する機能の全体 → 対象外としたもの**
- **提供する機能を一通り挙げる。** 最初に作った機能や、いちばん話題になった機能だけで終えない。
  第 7 章の機能一覧と見比べて、抜けている機能が無いようにする
- **例外的な話は書かない。** エラーの扱い・特別な入力・内部の工夫は、ここではなく後続の章に書く
- どれも文章で書く。**段落を「できること。」「やらないこと。」のような見出し語で始めない**
  (始めるとビルドが止まる)

## @io — 外部インターフェース(5.1 / 5.2)

**このシステムが、外部エンティティから何を受け付けて何を返すか、外部エンティティへ何を要求して
何を受け取るかを書く。** インターフェース 1 つは、**1 対の要求と応答**。1 つのインターフェースに
複数の要求をまとめない(API ならエンドポイントごと、コマンドならサブコマンドごとに 1 つ)。
5.1 の図・一覧表と 5.2 の詳細は、どちらもこの 1 か所から作られる。

```
@io
@self mdsite | CLI
@peer 利用者
@if 変換の実行 | 受付 | `python src/mdsite.py --input <入力フォルダ> --output <出力フォルダ>`
要求: 入力フォルダのパス、出力フォルダのパス
応答: 処理結果の要約、エラーメッセージ、終了コード
手段: コマンドライン引数で受け付け、標準出力・標準エラー出力と終了コードで応答する
形式: 正常時は標準出力に要約、異常時は標準エラー出力に 1 行。終了コードは 0 か 1
契機: プロセスの起動時に 1 回
用途: パスの妥当性を検証し、収集の起点にする（F-02）
エラー: E-02 E-03 — ファイルを書き込まずに終了コード 1 で終了する
検証: test_path_same_errors
@param --input | パス | 必須 | - | 実在するフォルダ | 変換元のフォルダ
@param --output | パス | 必須 | - | 入力フォルダと異なるパス | 変換先のフォルダ
@return 終了コード | int | 0 は正常、1 は異常
@peer 入力フォルダ notes/
@if メモの読み込み | 発行
要求: 入力フォルダ配下のファイルの読み込み
応答: メモの本文、付随ファイルのバイト列
…（残りの 6 項目）
@caption 入力フォルダは読み取りのみで変更しない（N-01）。
```

- `@self` はこのシステム自身。`|` の後ろは補足(省略可)
- `@peer` は外部エンティティ(利用者・外部サービス・ファイル・OS の機能)。同じ外部エンティティの
  インターフェースは 1 か所にまとめる。内部のモジュールは書かない(4.2 の役目)
- `@if 名称 | 受付か発行 | 書式` がインターフェース 1 つ。書式は省略できる
  - `受付`: 外部エンティティが要求し、このシステムが応答する(コマンド、API のエンドポイント、画面の操作)
  - `発行`: このシステムが要求し、外部エンティティが応答する(外部 API の呼び出し、ファイルの読み書き、OS の機能)
  - 名称は名詞で書く(「予約の登録」「時間表の取得」)。書式は呼び出しの形を `` ` `` で囲んで書く
    (`` `POST /api/bookings` ``、`` `kashikari add <品名> <貸出先>` ``)。別の書き方があれば「または」で並べる
- **ID(`I-01`…)は書かない。** 並び順から機械が振る。要求元と要求先も、`@peer` と `受付`/`発行` から
  機械が入れる
- 5.1 の図は、外部エンティティごとに要求と応答の矢印を 1 本ずつ描き、ID の範囲を付ける
  (「I-01〜I-16 要求」)。図の下に一覧表(ID・名称・要求元・要求先・要求・応答)が自動で入る

### インターフェースの項目

`@if` の下に 8 項目を書く。該当が無くても `なし` と書いて項目を残す。

| 項目 | 何を書くか |
|---|---|
| `要求` | **要求として渡されるデータの名前。** 名詞で短く書く(「予約の登録内容」「表示日」)。項目の一覧は `@param` に書く |
| `応答` | **応答として返されるデータの名前。** 返すものが無ければ `なし`(図に応答の矢印が出ない) |
| `手段` | 通信や受け渡しの方式(コマンドライン引数 / 標準出力 / HTTP / ファイルの読み書き / 画面の操作) |
| `形式` | データの表現と規約(引数の書式・リクエストボディの形式・ステータスコード・終了コード) |
| `契機` | いつ発生するか(起動時に 1 回 / 操作のたび / 完了時) |
| `用途` | 要求を受けて何を行うか。**対応する機能を `F-nn` で書く**(書いた機能を持つユースケースが、6 章のデータフロー図でこの外部エンティティと結ばれる) |
| `エラー` | 失敗したときの動作。`E-nn` でエラー仕様に繋ぐ |
| `検証` | この記述を固定しているテスト名。`@spec` と同じ書き方 |

- **`@peer` の直下(最初の `@if` より前)に書いた項目は、その外部エンティティのインターフェースに
  共通の値になる。** `要求` と `応答` は共通にできない
  - `手段` `形式` `契機` `用途`: `@if` の下に同じ項目を書けば、そのインターフェースだけ置き換わる
  - `エラー` `検証`: **共通の分が、各インターフェースの記載に足される。** 全インターフェースに共通する
    テスト(出力の形式、文字コードなど)と、エラー時の共通の動作(「データファイルを変更せずに終了コード 1
    で終了する」)は `@peer` の直下に 1 回だけ書き、`@if` の下にはそのインターフェース固有のエラー ID と
    テスト名だけを書く。`エラー: なし` と書いたインターフェースには、共通のエラーは足されない
- **`@peer` の名前を 6 章の `@store` の名前で始めると、データストアとして扱われる**(「データファイル
  data\kashikari.json」)。データフロー図では外部エンティティではなくデータストアの側に描かれる
- **`要求`・`応答` と `用途` を混ぜない。** 「何のための指定か」は `用途` に書く
- **ファイルやデータベースの項目は、6 章の `@schema` に書く。** 5 章には読み込みと書き込みの
  インターフェースだけを書き、同じ項目を 2 か所に書かない

### @param / @return — 要求パラメータと応答項目

```
@if 予約の取り消し | 受付 | `POST /api/bookings/cancel`
要求: 取り消し対象の予約
応答: 取り消し結果
…
@param id | int | 必須 | - | 有効な予約の予約 ID | 取り消す予約
@param scope | str | 任意 | one | one・following | 取り消す範囲
@return cancelled | list | 取り消した予約(id・date・label)
```

- `@param` は要求のパラメータで、6 列で固定: `名前 | 型 | 必須 | 既定 | 取りうる値 | 説明`。
  `必須` の列は `必須` か `任意`。既定や取りうる値が無ければ `-`
- `@return` は応答の項目で、3 列で固定: `名前 | 型 | 説明`
- どちらも書かなくてもビルドは通る。引数・パラメータを取るインターフェースには `@param` を書く。
  `@return` は、ソースで確かめた項目だけを書く

## @paths — インターフェース詳細(5.2)

5.2 に `@paths` とだけ書く。`@io` に書いたインターフェースが、第 8 章の機能仕様と同じブロック形式で
並ぶ。中身は `@io` が持つので、ここには何も書かない。

## @purpose — 目的(3.2 ユースケース)

**目的 1 つが、ユースケース 1 つ。** 見出しの下に 3 つの項目を書く。**「誰が、対象に対して、
概要を行う」**と続けて読める形にする。3 つとも必須で、欠けるとビルドが止まる。

```
@purpose P-01 貸出を登録する
誰が: 利用者
対象: データファイル
概要: 貸出の事実を残すために、品名・貸出先・返却期限を 1 回のコマンド実行で登録する
@flow P-01
…
```

| 項目 | 何を書くか |
|---|---|
| `誰が` | このユースケースのアクター。複数なら `、` で区切る。仕様書では「アクター」の列に出る |
| `対象` | アクターが操作する対象。どこに書くのか・何を見るのか・何を変えるのか、の「どこ・何」。6 章のデータストアや画面の名前で書く(扱う中身の項目ではない)。**同じものには同じ名前を使う**(図と表を分ける軸になる) |
| `概要` | 何のために、何をするのか。1 文で書く |

- **処理の順番の要約を書かない。** 「〜して、〜して、〜する」は流れ(`@flow`)の役目
- **例外的なことは書かなくてよい。** 止まる条件や特別な場合は、流れと 9 章に書いてある
- **利用者の目的で切る。命令・画面・機能の単位では切らない。** 同じ目的を果たす別のコマンドは同じ
  ユースケースに入れる。それだけでは目的が完結しない途中の操作は、独立させずに流れの中の手順にする
- 3.2 の先頭に、ユースケース図と一覧表(対象・ID・ユースケース・誰が・概要・別紙へのリンク)が
  自動で入る。図と表は原稿に書かない
- **図と表は `対象` ごとにまとめて出る。** ユースケース図では対象ごとのパッケージ、一覧表では対象ごとの行の
  まとまり、6 章のデータフロー図では対象ごとに 1 枚になる。ユースケースの数が多くても見渡せるように
  するためで、ユースケースの単位そのものは変えない(追加・変更・削除を 1 つにまとめる必要はない)
- ID は `P-01` から連番。目的を定義したら、**対応する流れを必ず書く**(無ければビルドが止まる)

**同じ番号を 4 か所で使う。** 3.2 のユースケース、6 章のデータフロー図のプロセス、別紙の
流れ図、7 章の工程の列は、どれも `P-01` などの目的の番号で結ばれる。

## @flow — 処理の流れ(3.2 に書き、別紙に出る)

**流れ図は仕様書の本体には出ない。** 同じ原稿から別紙 `spec-flow.html` を作り、そこに目的ごとに
1 枚ずつ出す。別紙では左に流れ図、右に工程ごとの説明(機能の概要・処理・止まる条件・実装)が
並び、工程を選ぶと対応する説明が示される。本体の 3.2 には、別紙のその流れへのリンクが出る。
書く場所と書き方は変わらない。

**別紙の図は簡略に描かれる。** 工程は番号の丸、判断はひし形で、工程の名前は図に出ない(右の説明に
出る)。**判断の条件と枝のラベルは、図にそのまま出る。** `判断` には、何で分かれるのかが読める条件を
疑問文で書き(「総務パスワードが設定されているか？」)、`枝` には答えを書く(「はい」「いいえ」)。
分岐には流れごとに記号(A, B, …)が振られ、右の説明欄に「分岐 A」として、条件と、答えごとの進み先
(「02 総務パスワードの初回設定 を実行し、03 受け付けの開始 へ進む」)が自動で出る。記号は原稿に書かない。
丸の右にはラベルが付き、`実装:` を書いていればそのモジュール、無ければ機能 ID になる。
`例外` は、ひと続きの流れ(本線・枝・経路)ごとに 1 つの「エラー」へ線が集まり、例外の中に書いた
工程や終了は図に出ない(右の「エラー条件」に出る)。「エラー」は、最後にエラーが起きる工程の左に置かれる。下の表の「図での形」は、この簡略な形に
読み替える。


**流れは目的ごとに 1 つ。** 見出しで目的を指す。

```
@flow P-01
端子 アプリを開く
工程 端末の前提を確かめる | F-01
判断 保存されたトークンがあるか？
枝 いいえ
  工程 ログイン画面へ送る
  終了 ログインするまで扱えない
枝 はい
工程 保存トークンでログイン状態に戻す | F-02
例外 トークンを復号できない | E-06
  工程 再ログインを求める
  終了 ログインするまで扱えない
例外終わり
並行
経路
  工程 前回済んでいない同期を片付ける | F-03
経路
  工程 新譜を探す | F-04
合流
端子 箱一覧を扱える
@caption 前提を満たさない項目があっても止めない。断り書きを添えるだけ。
```

| 語 | 意味 | 図での形 |
|---|---|---|
| `端子` | 開始・正常終了 | 角丸 |
| `工程` | 処理。`\| F-01` でその機能に紐づく | 角箱＋番号 |
| `判断` `枝 <ラベル>` | 排他分岐。2 度目の `枝` で本線に戻る | 菱形 |
| `終了` | 異常終了 | 太枠の角丸 |
| `待機 <条件>` | 時間や状態を待つ | 琥珀色の箱 |
| `繰り返し <条件>` … `繰り返し終わり` | 前判定(while) | 破線の枠。条件は上 |
| `繰り返し` … `繰り返し終わり <条件>` | 後判定(do-while) | 破線の枠。条件は下 |
| `例外 <条件> \| E-nn` … `例外終わり` | 直前の工程から離脱する | 破線で抜ける |
| `並行` `経路` … `合流` | 同時に走り、全部の完了を待つ | 太いバーで挟む |
| `順不同` `経路` … `順不同終わり` | 逐次だが順序は決まっていない | 淡いバーで挟む |

- 工程には自動で `01` から番号が振られる。**目的ごとに振り直す**。第 7 章には
  `P-01:03`(目的 P-01 の 3 番目の工程)の形で出る
- **端子には番号を振らない。** 分岐の枝・繰り返し・並行の中の工程は番号を持つ
- **流れの粒度は機能。分岐を無理に作らない。** `判断` を書くのは、分かれた先がそれぞれ別の工程として
  意味を持つときだけ。省ける引数の有無や書式の違いのように、1 つの機能の中で収まる分かれ目は
  書かない(その機能の `処理:` に書く)。分岐の無い 1 本道の流れは、それで正しい
- **分岐の枝の中の工程も番号を持つ。** 機能 ID(`| F-05`)と `例外` を書ける。分かれた先で別の
  機能が動くときは、枝の工程にその機能の ID を添える
- 第 7 章の「工程」列はここから作られる。**第 8 章の全機能が、いずれかの流れの工程に
  現れること**(どの流れにも現れない機能があるとビルドが止まる)。1 つの機能が複数の
  流れに現れてよい

書けない組み合わせ:

- 分岐(`枝`)の中に `並行` `順不同` `繰り返し` は書けない(`例外` は書ける)
- 繰り返しの中に `判断` は書けない
- `例外` は `工程` か `待機` の直後にだけ置ける
- **1 つの工程に `例外` は 1 つだけ。** 複数のエラーで離脱するなら 1 つの `例外` に ID を並べる
  (`例外 入力が不正 | E-01 E-02`)。2 つ目を書くとビルドが止まる
- `並行` `順不同` の直後は `経路`。経路は 2 つ以上必要

## @graph — モジュール結合図(4.2)

**4.1 構成要素は、モジュールと役割の表。** 役割は「〜する」「〜を行う」のように動詞で終える
(名詞で終えるとビルドが止まる)。`実装:` を書いていれば、モジュールごとの「関わる機能・エラー」の
列が自動で足される(1 列目をソースのファイル名にしておく)。

**4.1 に挙げた構成要素(モジュール)どうしの、呼ぶ・参照する関係を書く。** 静的な関係だけで、
時系列は 3.2 の役目。

```
@graph
@hub commands.py | 命令ごとの流れを持つ中心
kashikari.cmd -> kashikari.py: 起動
kashikari.py -> commands.py: 引数と今日の日付
commands.py -> storage.py: 読み書き
```

- 関係は `源 -> 先: ラベル` の 1 行 1 本。**中心を通らない関係も書ける**
- 同じ 2 要素の往復は 1 本の双方向の辺にまとまる
- `@hub` は強調したい要素(任意)。指定しなくても図になる
- **モジュールは、ソースのファイルに限らない。** 起動用のスクリプト(`.cmd` など)や、同梱する
  部品もモジュールとして 4.1 に挙げ、ここに描く
- **外部エンティティとデータストアは描かない。** 利用者・外部サービス・ファイルとのやり取りは 5 章、
  データの出入りは 6 章のデータフロー図に書く。5 章の外部エンティティや 6 章の `@store` の名前を書くと
  ビルドが止まる
- **配置は自動で決まる。** 辺の交差が最も少なく、線が短くなる並びを探す。位置は書かない
- **辺は結ぶ 2 つ以外の箱を貫かない。** 貫通は交差より重く扱って配置で避け、それでも
  避けきれない組は箱をよけて 1 か所で折れる。要素の上を線が走ることは無い
- **4.1 に挙げた要素はすべてここに現れること**(現れないとビルドが止まる)
- ビルドに `--code` を付けると、ソースの `import` から読んだ参照が、ラベルの無い線として足される。
  機械が読める関係を手で写す必要はない(手で書くのは、`.cmd` からの起動のように読めないものだけ)
- 箱の左の色はモジュールの色で、別紙の処理フロー図のラベルと同じ色になる。モジュールを選択すると、
  関係する矢印と接続先のモジュールだけが強調表示される

## @store / @schema — データ仕様(6)

**データストアごとにセクションを作る。** テーブルや JSON の単位で分ける。

```
@store 貸出レコード | データファイルの records の要素
@p 貸出 1 件の情報を保持する。
@schema
id | レコード番号 | int | 1 | - | - | ○ | - | - | 登録順に採番する通し番号。再利用しない
item | 品名 | str | 1 | 100 | 文字 | - | - | - | 貸出物の名称
due | 返却期限 | date | - | - | - | - | - | - | 返却を受ける予定日。未指定は null
tags | タグ | list | 0 | - | 件 | - | - | - | 分類用の文字列の並び
```

- **`@store` の下の説明(`@p`)には、そのデータが何を保持するかだけを書く。** 運用の手順
  (入れ替えのときに何を残すか、ほかのソフトで開かない、など)や、処理の説明はここに書かない
  (手順は README、前提は 10 章か 4.3、処理は 8 章)

`@schema` は 10 列で固定:

| 列 | 書き方 |
|---|---|
| データ名 | 実装上の名前(列名・キー名)。`lent_on` のように、ソースやファイルに出てくるとおりに書く |
| 和名 | 仕様書での呼び名(「貸出日」)。第 2 章の用語と合わせる |
| 型 | `str`・`int`・`float`・`bool`・`date`・`list`・`dict` など、実装で使う型の名前で書く。「並び」「入れ子」のような言い換えをしない(日本語で書くなら「文字列」「整数」「リスト」) |
| 下限値 / 上限値 | 数値。無ければ `-` |
| 単位 | 文字・バイト・件・エポックミリ秒 など。無ければ `-` |
| 主キー | `○` か `-` |
| 外部キー | `○` か `-` |
| 参照先 | 参照するデータストアの名前。複数なら `箱, カタログ`。無ければ `-` |
| 説明 | 何を入れるか |

- 外部キーが `○` なら参照先が必須。`-` なら参照先も `-`
- **参照先は `@store` で定義したデータストアの名前**(無い名前を書くとビルドが止まる)
- 参照先の末尾に `+` を付けると「親 1 つにつき子が 1 件以上」。既定は 0 件以上
  (親を作った直後は子が無いのがふつう)

**6 章の先頭には ER 図が自動で入る。** 関係は原稿に書かない。`@schema` の外部キーが
唯一の出どころで、図と表が食い違わない。IE 記法で描き、参照される側が「1」、
参照する側が「0 以上」(`+` を付けたときだけ「1 以上」)。

## @dfd — ユースケースごとのデータフロー図(6)

**6 章には、全体のデータフロー図(プロセスは 3.2 の目的)が自動で入る。** そのあとに、目的ごとに
中の処理を分けた図(下位のデータフロー図)を描く。`@dfd P-nn` を書いた目的は書いたとおりに描き、
書いていない目的は流れに現れる機能(`F-nn`)を 1 つずつ円にする。**目的ごとに `@dfd` を書く。**
機能 1 つを円 1 つにしただけでは、中でデータをどう受け渡しているかが読めない。

```
@dfd P-03
P-03.1 登録内容の検査 | F-06
P-03.2 重複の確認 | F-06
P-03.3 予約の追加 | F-06
P-03.4 データファイルへの保存 | F-15
社員(クライアント PC のブラウザ) -> P-03.1: 予約の登録内容
会議室 -> P-03.1: 会議室の一覧
P-03.1 -> P-03.2: 規則に合う予約の登録内容
予約 -> P-03.2: 同じ会議室・同じ日の予約
P-03.2 -> P-03.3: 重複の無い予約の登録内容
P-03.3 -> P-03.4: 予約を加えた作業用の複製
P-03.4 -> データファイル: 変更後のデータファイル
P-03.3 -> 社員(クライアント PC のブラウザ): 登録した予約の ID
P-03.1 -> 社員(クライアント PC のブラウザ): 規則に合わない理由のメッセージ
```

- **処理の行は `P-nn.k <処理名> | <機能>`。** 番号は目的の番号に `.1` `.2` … を付ける。処理名は
  「〜の検査」「〜の追加」のように、データに何をするかを名詞で書く。機能(`F-nn`)は任意で、
  その処理を受け持つ機能を書く(1 つの機能を複数の処理に分けてよい)
- **流れの行は `<元> -> <先>: <データの名前>`。** 元と先は、この `@dfd` の処理の番号・5 章の
  外部エンティティ(`@peer` の名前のとおり)・6 章の `@store` の名前のどれか。処理の行を先に書く
- **片方の端は必ず処理にする。** 外部エンティティどうし、データストアどうし、外部エンティティと
  データストアを直接つなぐとビルドが止まる
- **どの処理にも、入る流れと出る流れを 1 本以上書く。** 受け取るだけ・出すだけの処理はビルドが止まる
- **データの名前を必ず書く。** 「なし」のような、データの流れない要求は書かない
- **処理の粒度は、データが形を変える単位にする。** 検査・照合・計算・組み立て・保存のように、
  入るデータと出るデータの名前が変わるところで分ける。関数の単位まで細かくしない(目安は 3〜7 個)
- 上位の図(全体の図)でその目的につながる外部エンティティとデータストアは、下位の図にも現れるようにする

## @spec — 機能仕様(第 8 章)

```
@spec F-01 出力初期化 | 確定
概要: 書き出し前に出力フォルダの中身を全削除する
実行契機: 実行前検証の完了直後、書き出し処理の前
前提条件: 9 章の判定条件すべてに該当しないこと（N-02）
入力: 出力フォルダ
処理: 出力フォルダ配下の全ファイル・全フォルダを削除する
出力: 空の出力フォルダ
エラー: E-07 — 削除できないファイルが存在する場合、中止する
検証: test_output_is_wiped test_idempotent
```

- 見出しは `@spec <ID> <機能名> | <確定状況>`。確定状況は **確定 / 暫定 / 未固定**
- **機能の粒度は、利用者に提供する機能の単位にする。** ユースケース・流れの工程・データフロー図と
  同じ大きさで、「貸出の登録」「貸出中一覧の表示」「レコードの削除」のように数える。文字コードの
  固定・列の切り詰め・書式の読み分けのような、機能の内側の細かい処理は機能にせず、その機能の
  `処理:` に書く。複数の機能から使う共通の処理(起動・読み込み・保存・入力の解析)は、それぞれ
  1 つの機能としてよい
- **機能名は名詞で書く**(「記録の読み込み」「一覧表示」「返却の取り消し」)。文にしない。
  「〜する」で終わる、「を」を含む、「の」が 2 回以上、読点・かっこを含む名前はビルドが止まる。
  修飾は「〜の〇〇」1 つまで。補足は `概要:` に書く
- **ID の順序は 3.2 の各 `@flow` の中で、工程に添えた先頭の ID が小さい順**
  (`@flow` ごとに独立。1 つの工程に `| F-04 F-05` と複数添えた 2 つ目以降は順序の判定に
  入らない)。実装の実行順でも話題順でもなく、**3.2 に並べた工程の順**。流れを先に書き、
  その順に `F-01` から振る
- **機能名と `概要` は「他の欄は読まれない」前提で書く。** 第 7 章の機能一覧に出るのは
  `機能` と `概要` だけで、`処理` `実行契機` `入力` `出力` は載らない。機能名は説明なしで
  意味が通じる語にし、内部の処理名・変数名をそのまま機能名にしない。`概要` は 1 行で
  機能の全体が見えるように書く(続きを読まないと分からない書き出しにしない)
- **`概要` の主語は「利用者の手元で何がどうなるか」にする。** ツールの内部で何をするか
  (「出力先を検査する」「記録ファイルを照合する」)ではなく、その結果利用者に何が起きるか
  (「前に作ったページを消してから作り直すので、消したメモのページが残らない」)を書く。
  利用者が何かをする機能は、何を聞かれ、何をすればよいかまで書く。語は機能名と同じく、
  インタビューで利用者が使った語を使い、作る側の用語(除外規則・正規化等)を持ち込まない
- **機能名を変えたら旧語で原稿全体を grep する**(SKILL.md 手順 6)。章をまたいで旧語が
  残ると、読者には別の機能に見える
- `概要` `実行契機` `入力` `出力` `検証` は必須。該当が無くても `なし` と書いて項目を残す
- `前提条件` `処理` `エラー` は省略可(省略すると「なし」になる)
- 同じ項目を複数行書くと箇条書きになる。`処理` は書いた順の番号付きになる
- **工程番号は書かない。** 3.2 の流れに `| F-01` を添えることで対応づく

### 検証欄の書き方

| 書き方 | 意味 | 判定 |
|---|---|---|
| `test_a test_b` | 人が決めて E2E で固定した | 確定 |
| `? test_a` | 現状を観測して固定しただけ(特性化テスト) | 暫定 |
| `なし` | 決定はあるが試験が無い | 未固定 |

テスト名は識別子として妥当なら何でもよい(日本語のテスト名も書ける)。

**推測で `確定` を書かない。** 人が確認していない振る舞いは `?` を付ける。ここが
第 13 章の内訳になり、仕様書のどこが脆いかの地図になる。

**任された所に AI が仮に置いた値(文字数・件数・時間などの数値や線引き)は、試験で固定して
あっても `確定` にしない。** 検証欄に `?` を付けて暫定にし、`概要` にも「(仮に 30 件。
見て直す)」のように仮であることを書く。試験で固定したのは AI が置いた値であって、利用者が
決めた値ではない。利用者が読んで「決めた覚えがない」と言う値は、確定に見せてはならない。

## @rows — ID 付き条項表

列は章が決める。モデルは行だけを書く。ID は各章で `01` から連番。

| 章 | 列 |
|---|---|
| 9 エラー仕様 | `E-nn \| 判定条件 \| メッセージ内容 \| 流れ \| 検証` |
| 10 非機能要件 | `N-nn \| 分類 \| 条件 \| 検証` |
| 11 適用範囲外 | `X-nn \| 対象外の事項 \| 理由` |
| 12 設計判断 | `D-nn \| 決定 \| 理由` |
| 14 未確定事項 | `U-nn \| 項目 \| 現在の動作 \| 確定に必要な確認事項` |

検証欄の書き方は `@spec` と同じ。判定は自動で付く。

### 9 章の「流れ」列

**そのエラーが 3.2 のどこで起きるかを書く。**

- 流れが変わるもの(そこから離脱する・別の経路に入る)は、3.2 の工程に
  `例外 <条件> | E-nn` を添えたうえで、この列にどの流れかを書く
  (例: `P-04 の書き込みから離脱`)
- 流れが変わらないもの(その操作が失敗するだけで、次に進む道筋は同じ)は
  **`流れ不変`** と書く

空欄にはできない。書いていないと、**見ていないのか、見た上で描かないと決めたのかが
区別できない**。第 8 章の機能が「どの流れにも現れないとビルドが止まる」のと同じ規律を、
エラーにも効かせる。

この列に流れを書いたのに 3.2 に `例外` が無ければビルドが止まる。

## 実装への紐づけ(任意。保守する人のための層)

仕様書は「何ができるか」を E2E を正として書く。ここは同じ項目に、**それがコードのどこにあるか**を
足す。書かなければ今までと同じ仕様書が出る。**説明文は足さない。** 書くのは場所だけで、
実在・コード・図・一覧はビルドがソースから作る。

```
@spec F-13 返ってきた・あげたにする | 確定
…
検証: test_back_by_number
実装: commands.py:_end records.py:end
読む: 記録のファイル
書く: 記録のファイル
```

| 書く場所 | 書き方 | 何になるか |
|---|---|---|
| `@spec` の `実装:` | `ファイル:関数` を空白区切り。ファイルは `--code` のフォルダからの相対 | 第 8 章の「実装」の行。開くとその関数のコードが出る |
| `@spec` の `読む:` `書く:` | 第 6 章の `@store` の名前を 1 行に 1 つ | 第 6 章に「データフロー図」。プロセスは 3.2 の目的、外部エンティティは 5 章から入る。目的ごとの図は `@dfd` で書く |
| 第 9 章の `@impl` | `E-01 \| ファイル:関数` を 1 行に 1 つ | 第 9 章に「発生箇所」の列 |

```
## 9 エラー仕様
@rows
E-01 | … | … | … | test_x
@impl
E-01 | dates.py:parse_due
```

ビルドに `--code <ソースのフォルダ>` を付けると、次が加わる。

- **実在の検査。** 指した関数がソースに無ければビルドが止まる(名前を変えた・消したに気づける)
- **4.2 モジュール結合図への追加。** `import` から読んだ参照の線と、モジュールごとの役割・関わる機能の表
- **第 15 章 保守のための情報。** 環境変数を読む所・ファイルを書く/消す所・例外を上げる所・失敗を
  まとめて受ける所をソースから拾い、仕様のどの機能・エラーに当たるかを並べる。当たるものが
  無ければ「仕様に記載なし」と出る。**出たら、仕様に足すか、第 14 章に回すかを決める**

機械で調べられるのは Python のソースだけ。ほかの言語は、`実装:` に書いた名前がファイルの中に
あるかだけを確かめる(コードの抜粋・参照の線・第 15 章は出ない)。

載るコードは `実装:` と `@impl` で指した関数だけで、ソースの全文は入らない。コードを見せたくない
相手に渡すときは `--code` を付けずにビルドする。

## 言葉づかい

**仕様書の地の文は、システムの用語で書く。** 利用者との会話で使った言い方を、そのまま持ち込まない。

| 書かない | 書く |
|---|---|
| (コマンドを)打つ・叩く | 入力する・実行する |
| 黒い画面 | コマンドプロンプト・ターミナル |
| 知らせ・お知らせ | メッセージ・エラーメッセージ・警告 |
| 結果 | 実行結果・出力 |
| 記録・メモ(保存するもの) | レコード・データファイル(題材の名前を付ける) |
| 見る・書く・直す・消す | 表示(参照)・登録・更新(訂正)・削除 |
| 今の・前の・新しい | 現在の・変更前の・変更後の |
| 決まり・やり方 | 規則・手順・方式 |
| 入れ物・置き場 | データストア・保存先 |
| 止まる | 処理を中止する・異常終了する |
| 〜してしまう・さっと・ちゃんと | 使わない(条件や数値で書く) |

- **データと状態には名前を付け、第 2 章で定義する。** 「もの」「相手」「約束の日」ではなく
  「品名」「貸出先」「返却期限」。状態も「貸している」ではなく「貸出中」
- **用語と名称は、採点して決める**(`references/term-scoring.md`)。意味の正確さ・一般性・名詞性・
  一意性の 4 基準で全件に点を付け、代替案と比べて決める。下の項目は、その基準の具体例である
- **用語は原則として名詞にする。** 修飾は、形容詞などを 1 つ添えるところまでを特例として認める
  (「長期貸出」「変更不可の回」)。「変えられない日」「入らない日」のように、状態を説明する文を
  そのまま用語にしない。画面には平易な言い方(「変えられない日があります」)を出してよいが、
  仕様書の地の文では名詞の用語を使い、画面上の表記は第 2 章に対応として載せる
- **画面の見出し・列名は、画面のとおりに書く。** 一覧の列を説明するときは、実際に表示される
  見出し(「番号」「もの」「相手」)をかぎかっこで引用し、仕様書の用語との対応は第 2 章か
  その行の説明に書く。仕様書の用語に置き換えた列名を、画面に出るかのように書かない
- **画面に出る文言は、かぎかっこで引用するときだけ元のまま書く。** 仕様書の用語と画面上の表記が
  違うときは、第 2 章の用語定義に両方を載せて対応づける(例: 「返却済み: 画面上の表記は『返ってきた』」)
- **要求と応答(5 章)はデータの名前で書く。** 「打った言葉 / 結果と知らせ」ではなく
  「コマンドライン引数 / 実行結果・エラーメッセージ」
- **代名詞と抽象的な語を使わない。** 「それ」「もの」「相手」「中身」「所」ではなく、指している対象の
  名前を書く
- **一般に定義のある図・記法・技術の用語は、その用語のまま使う。** 独自の言い換えをしない
  (データストア・エンティティ・プロセス・アクター・リクエスト・レスポンス・ステータスコード・
  レコード・テーブル・カラム・バージョン)。「入れ物」「版」「見出し(HTTP ヘッダーの意味で)」と書かない
- **漢字一文字の語を単独で使わない。** 「枠」「札」「行」「表」「形」「印」「版」は、「時間枠」
  「レコード」「一覧表」「形式」「バージョン」のように熟語か用語にする
- **和語の動詞を名詞にした言い方を用語にしない。** 「続けて間違えた回数」ではなく「連続失敗回数」、
  「試行制限の終了日時」ではなく「制限解除日時」
- **図の脚注(`@caption`)に、記法の説明を書かない。** 「矢印は呼ぶ向き」「箱はモジュール」のような
  図の読み方や、図がどう作られたかは書かない。脚注に書くのは、図だけでは伝わらない仕様上の補足に限る
- 文体は「である」体。名詞止めでよい

## 書いてよいこと・いけないこと

- 第 8 章・9 章・10 章に書けるのは、E2E に対応する試験があるものだけ。試験が無いものは
  `なし` と書いて `未固定` にするか、第 14 章へ移す
- 第 2 章・11 章・12 章は試験に対応しなくてよい(用語・スコープ外・設計判断は試験の
  対象ではない)
- 第 12 章は決定と理由を 1 行ずつ。ADR 全件ではなく、利用者の理解に効くものだけ
- 形容詞で逃げない。「壊れない」ではなく「書き込み・削除・属性変更を行わない」と書く
