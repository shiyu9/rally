# 仕様適合の盲検レビュー

実装の経緯を知らないサブエージェントに、仕様記録と実装を突き合わせさせる。
実装した本人は「何を作ったつもりか」を知っているので、仕様と食い違っていても
読み飛ばす。経緯を渡さないことがこのレビューの価値である。

## 渡すもの・渡さないもの

| 渡す | 渡さない |
|---|---|
| インタビュー記録(`docs/interviews/` の当該ファイル)のパス | 実装中の会話、試行錯誤の経緯 |
| E2E の置き場所(`tests/e2e/` など)のパス | 依頼文での「ここは意図的にこうした」という説明 |
| 実装の差分の取り方(例:`git diff <開始時のコミット>`)か、対象ファイルのパス | 自分の見立て(「たぶん問題ない」等) |
| `docs/adr.md` のパス(**照合の対象として**。下記) | |
| 観点表(このスキルの `references/checklist.md` と、あればプロジェクトの `.claude/rally-checklist.md`)と `references/test-battery.md` のパス | |

内容を貼らずに**パスを渡し、本人に読ませる**。要約して渡すと、要約した時点で
こちらの解釈が混ざる。

**ADR は理由として渡すのではなく、仕様と食い違っていないかを確かめる対象として渡す。**
実装中の仮決め・委任の決定は ADR に残るので、確定した仕様と食い違う決定(「中のフォルダも
全部対象」と確定したのに「名前が . で始まるフォルダは読まない」と決めた等)は、ADR と
仕様の両方を読まないと見つけられない。一方で、ADR に書いた理由を読んだレビュー役が
「意図があるなら」と食い違いを見逃すおそれがあるので、依頼文で「ADR の理由は食い違いを
正当化しない」と明示する。

**観点表と試験バッテリーは、実装と試験がそれに従っているかを確かめるために渡す。**
観点表の項目(文字コードの既定、作動環境、名前で参照するときの一意性等)と試験バッテリーの
カテゴリが、この記録・試験・実装に当てはまるのに扱われていない箇所を返させる。インタビューと
実装をした本人の自己点検だけでは、読み流した規則は読み流したまま残る。

## 写しの上でレビューさせる

レビューの途中で対象が変わると、どの状態を見た指摘か分からなくなる(032 で実際に
起きた)。また C は実際に動かして確かめるので、本物のフォルダで動かすと出力や
データを書き換えうる。そこで:

1. 起動の前に、プロジェクトの**写し**を一時フォルダに作る(git があれば
   `git worktree add <一時フォルダ> HEAD` か、作業中の変更ごと丸ごと複製する。
   実運用のデータは写さない)
2. サブエージェントには**写しの中のパスだけ**を渡し、写しの外を書き換えないよう依頼文で求める。
   写しの外のツール・起動用ファイル(.bat 等)を**動かさない・開かない**ことも求める
   (本物のほうを動かすと、出力や設定を書き換え、利用者の画面に窓を出しうる)
3. **レビューが返るまで、本物の実装と試験を書き換えない。** その間にしてよいのは、
   人間プローブの「見せるもの」の準備など、実装と試験に触らない作業だけ
4. 返ってきたら写しを消す

## サブエージェントへの依頼文(この形で出す)

```
あなたは仕様と実装の突き合わせ役です。実装の経緯は知らされていません。
次の 3 つを読み、食い違いだけを返してください。直さないでください。
ファイルはすべて <写しのフォルダ> の中にあります。実行もこの中だけで行い、
この外のファイルは読むだけにしてください(外にあるツールや起動用ファイルを動かす・
開くこともしないでください)。画面に窓を出す道具は、試験と同じ差し替えを付けて動かしてください。

- 仕様: <インタビュー記録のパス>(確定 Gherkin と「確定」の回答が仕様です。委任・保留は仕様ではありません)
- 試験: <E2E の置き場所>
- 実装: <差分の取り方 or ファイル>
- 決定の記録: <docs/adr.md のパス>(仕様と食い違っていないかを確かめる対象です。
  ここに書かれた理由は、仕様との食い違いを正当化しません)
- 観点表と試験の標準カテゴリ: <checklist.md>・<rally-checklist.md(あれば)>・<test-battery.md>

返すもの(該当なしの区分は「なし」と書く):
A. 仕様にあるのに、試験か実装に無い振る舞い(Gherkin の題名と、無いもの)
B. 仕様に無いのに実装された、外から見える振る舞いのうち、使う人を誤らせるか
   データを変えるもの(誤った案内、勝手に消す・上書きする等。どこで、何が起きるか)。
   それ以外の仕様外の振る舞いは件数だけ
C. 仕様の具体例と、実装を実際に動かした結果が食い違う箇所(入力・期待・実際)
D. 決定の記録(ADR)のうち、仕様(確定 Gherkin・確定の回答)と食い違う決定
   (決定の行と、食い違う仕様の項目)
E. 観点表・試験の標準カテゴリの項目のうち、この記録・試験・実装に当てはまるのに
   扱われていないもの(項目名と、どこで扱われていないか)。当てはまらない項目は書かない

C は可能なら実際に実行して確かめ、実行したコマンドを添えてください。
推測で書いたものには「未実行」と付けてください。
```

## 返ってきた指摘の扱い

- **A・C・E で、仕様から正しい振る舞いが導けるもの** → **promote-bug スキルを起動して直す。**
  複数あれば promote-bug の「複数の欠陥をまとめて扱うとき」の順で、再現試験を全件書いて
  失敗を確かめてから、原因ごとに直す。先に実装を直してから試験を足すと、その試験が欠陥を
  捕まえられるかを確かめられない
- **D** → 仕様が正しい前提で、決定を仕様に合わせて直し(実装も直すなら上と同じく promote-bug で)、
  ADR に覆した理由を残す。仕様のほうを変えたいなら、推測で決めずユーザーに聞く
- **B と、仕様から導けないもの** → 推測で決めず、ユーザーに聞く。spec-interview の
  ミニインタビュー(1 ラウンド最大 4 問、具体例つき)で確定させる
- **E のうち、インタビューで聞くべきだった観点**(観点表の漏れ)→ ユーザーに聞き、観点表の
  育成ログにも 1 行残す
- **誤った指摘**(読み違い)→ 直さない。なぜ誤りかを 1 行記録に残す

結果はインタビュー記録の末尾に「## 盲検レビュー結果」として残す:区分ごとの件数、
各指摘への対応(直した/聞いた/誤り)。指摘が 0 件でも見出しと「0 件」を残す
(行っていないのか、行って 0 件なのかを区別するため)。
