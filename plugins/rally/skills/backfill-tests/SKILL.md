# backfill-tests:後追いテストの補充

rally の正規ルートは「仕様(Gherkin)→実装→E2E」の順で進むが、現実には rally を
通さずに書かれた・変更されたコードが生まれる。このスキルはそのコードを後追いで
rally の管理下に戻す:テストの穴を棚卸しして補充し、確認できた振る舞いを
仕様記録(docs/interviews/・E2E)に合流させる。

最大の敵は**現状追認**である。仕様記録の無いコードにテストを書くことは、
「現状の挙動=正しい仕様」と暗黙に宣言することに等しい。バグ入りの挙動を
テストで固定すると、回帰検知どころかバグを守るテストになる。
そこで期待値の**出所**を常に明示する。

## 絶対のルール

1. **期待値を推測のまま正式テストにしない。** 全てのアサーションの期待値は
   次の三択のどれかであること:
   (a) 既存の仕様記録(Gherkin・インタビュー記録・ADR)から導出した、
   (b) ユーザーに確認して確定した、
   (c) **特性化テスト**として明示マーク付きで固定した。
   AI の推測を無印の正式テストとして書くことは禁止(現状追認の固定化)。
2. **「これはバグでは」と思った挙動は固定しない。** 正式テストにも特性化テストにも
   せず、ユーザーに報告する。バグと確定したら、期待される正しい仕様を
   「失敗を期待する」再現試験として置き(手順 5)、修正は promote-bug スキルで
   別途行う。
3. **実装コードを変更しない。** このスキルの成果物はテストと記録だけ。
   リファクタや修正をしたくなったら、その旨を報告して別タスクにする。
4. **実データを変更しない。** 対象プロジェクトに実運用のデータファイルがあるとき、
   挙動の観測もテストの実行も、一時ディレクトリ・作業コピーに隔離して行う。
   実データは読み取り以外で触らない。

## 手順

### 1. 対象と既存資産の把握

- 対象コードを特定する(ユーザー指定、または git log / diff から
  仕様記録なしに追加・変更されたものを探す)
- 既存資産を読む:既存テスト(単体・E2E)、`docs/interviews/`、`docs/adr.md`、
  `.feature`(あれば)。「仕様が確定済みの振る舞い」と「テストで守られている振る舞い」を
  先に把握する

### 2. ギャップの棚卸し

- 対象の**観測可能な振る舞い**を列挙する(コマンド・API・入出力・ファイル生成)。
  コードを読んだ推測で書かず、**実際に実行して観測する**(実行は一時ディレクトリ・
  作業コピーで — 絶対のルール 4)
- 既存テストがカバーしている振る舞いを除外し、不足一覧を作る
- 機械的試験の不足も列挙する:spec-interview スキルの
  `references/test-battery.md`(このスキルからの相対パス:
  `../spec-interview/references/test-battery.md`)の該当カテゴリを対象に当てる

### 3. 期待値の出所で三分類する

不足一覧の各項目を、期待値がどこから来るかで分類する:

| 出所 | 扱い |
|---|---|
| 仕様記録から導ける | そのまま正式テスト化(手順 5 へ) |
| 導けないが**中核**の振る舞い | 観測結果を Gherkin にしてユーザーに確認(手順 4 へ) |
| 導けない**周辺**の挙動 | 特性化テストとして明示マークで固定(手順 5 へ) |

中核/周辺の目安:その機能を使う目的に直結する振る舞い・データを壊しうる振る舞い
(保存・削除・集計の正しさ)は中核。表示の細部・エラーメッセージの文言・
ヘルプの体裁などは周辺。

### 4. 確認ラウンド(ミニインタビュー)

- 観測した現状の挙動を Gherkin(具体例)に落とし、「この挙動は正しい仕様か」を
  **1 ラウンド最大 5 問**で確認する(AskUserQuestion が使える環境ではそれを使う)
- 回答は spec-interview と同じ三分類で受ける:
  - **確定(正しい)** → 正式テストへ。Gherkin を仕様記録に合流(手順 6)
  - **「それはバグ」** → 現状挙動を固定せず、バグ再現テストとして扱う(手順 5。
    修正は promote-bug で別途。完了報告に含める)
  - **委任・保留** → 特性化テストへ(委任は仮決め内容を一言明記する)
- 対象が大きくても**質問攻めにしない**。確認するのは中核だけに絞り、
  残りは特性化テストに回す。何を確認せず特性化に回したかは手順 6 の記録に残す

### 5. テストの実装

- **正式テスト**:導出済み・確認済みの振る舞いを E2E(プロジェクトの既存の置き場所)
  または単体試験として書く
- **バッテリー展開**:test-battery.md の該当カテゴリは**ユーザーに確認せず自動で**展開する
  (spec-interview の実装フェーズと同じ)。ただし期待値が仕様依存で導けないものは
  手順 3 の分類に従う
- **バグ再現テスト**:バグと確定した挙動は、**期待される正しい仕様**をアサーションにし、
  「失敗を期待する」マークを付けて置く(pytest なら
  `@pytest.mark.xfail(strict=True, reason="bug: <症状>")`。他言語でも同等の
  expected-failure 機構を使う):
  - スイートは green のまま再現が保存され、修正が入ると expected-failure が
    「通ってしまった」ことで赤くなり、マークの外し忘れも検知できる
  - **現状のバグ挙動をアサーションにしない**(それは現状追認)。書くのは正しい仕様の側
  - 修正はこのスキルでは行わない。修正着手時は promote-bug の手順(失敗確認→修正)に
    このテストをそのまま使う
- **特性化テスト**:現状の観測挙動をそのまま固定し、**明示マーク**を付ける:
  - テスト名またはコメントに `characterization` を含める
    (例:`# characterization: 現状の挙動を固定(仕様未確認 2026-07-27)`)
  - このマークは意味を変える:落ちたとき「仕様違反」ではなく「挙動が変わった」を
    意味する。意図的な変更で落ちたなら、それは仕様を確定させるチャンス
    (ミニインタビューでどちらが正しいか確定してから直す)
- 追加したテストを全て実行し、既存テストも含めて通ることを確認する。
  **特性化テストが落ちるなら観測が間違っている**(実行し直して書き直す)

### 6. 仕様記録への合流

`docs/interviews/YYYY-MM-DD-backfill-<対象>.md` に保存する:

- 対象と経緯(何が rally を通さず作られた・変更されたか)
- **確認済み Gherkin の全文**(「〜を参照」と書かず本文を埋め込む。
  記録単体で仕様が読めることが目的)
- 特性化として固定した挙動の一覧(=後日の昇格候補リスト)
- バグと確定した挙動の一覧(症状・期待される仕様・対応する再現テスト名。
  =修正時に promote-bug へ引き継ぐリスト)
- 確認せず特性化に回した領域(何を聞かなかったか)

確定した仕様(手順 4 の「確定」)があれば `docs/adr.md` にも一言残す。

### 7. 完了報告

追加した正式テスト数/特性化テスト数/報告したバグ数を 1〜3 行で報告し、
特性化テストの棚卸しを案内する:後日ユーザーが「この挙動でよい」と確認できたら
昇格する(下記)。

## 特性化テストの昇格

特性化テストは「仕様未確認」の暫定固定であり、確認が取れ次第正式化する:

- ユーザーが挙動を確認したら、マークを外して正式テストにし、
  Gherkin をインタビュー記録に追記する
- コード変更で特性化テストが落ちたら、それは仕様確定のチャンス。
  どちらの挙動が正しいかをミニインタビュー(選択肢 1〜2 問)で確定し、
  確定した側を正式テストとして固定してから実装・テストを直す
