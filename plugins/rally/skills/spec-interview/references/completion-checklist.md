# 実装の完了の定義と完了報告

spec-interview の実装フェーズで、完了の報告の前に読み、全項目を確かめる。

## 完了の定義


実装フェーズは次の 5 つが**すべて**揃ったときに完了とする。1 つでも欠けていたら完了の報告をしない:

1. 確定 Gherkin に対応する E2E が全部 green
2. 標準試験バッテリー適用結果表の 11 行が埋まっている(下記「バッテリー適用結果を記録に残す」)
3. `rally_test_audit.py` の (1)(表に書いた試験名の実在)が 0 件(下記「試験の実在と検出力の下限を機械で確かめる」)
4. 部分ミューテーションテストの記録が確定 Gherkin ごとに 1 行ずつある(下記「green の後に壊して確かめる」)
5. 盲検レビューの結果が記録にあり、指摘の対応(直した/聞いた/誤り)が書かれている(下記「部分ミューテーションテストの後に、盲検レビューを通す」)

## バッテリー適用結果を記録に残す

展開が終わったら、**11 カテゴリすべて**の適用結果をインタビュー記録
(`docs/interviews/` の当該ファイル)の末尾に追記する。1 行でも欠けていたら展開は未完了とする。

```markdown
## 標準試験バッテリー適用結果

| カテゴリ | 適用 | 試験名 / 該当なしの理由 |
|---|---|---|
| 1 境界値 | あり | `test_zero_items` `test_limit_plus_one` |
| 2 入力異常系 | あり | `test_empty_title_errors` |
| 3 データ永続化の頑健性 | なし | 実行間で状態を保持しないため |
| 4 冪等性・二重実行 | あり | `test_idempotent` |
| 5 状態遷移の違反 | なし | 状態を持たないため |
| 6 往復一致 | なし | シリアライズと復元の対を持たないため |
| 7 不変条件 | あり | `test_input_untouched` |
| 8 出力契約 | あり | `test_exit_code_on_error` |
| 9 環境依存 | あり | `test_non_ascii_stdout_on_cp932` |
| 10 スケール smoke | なし | 想定件数が 3 桁以下で性能上の懸念がないため |
| 11 試験そのものの検出力 | あり | `test_fixture_is_processed`(部分ミューテーションテストは「green の後に壊して確かめる」に記録) |
```

守るべきは 3 つ:

- **「なし」の行に理由を書かずに済ませない。** 理由が書けないカテゴリは、実は該当している。
  試験名を書けない性格の項目(カテゴリ 11 の「測る性質が、その実行経路に存在するか」等)は、
  「なし」の欄に**どの経路で採ったか**を 1 行書く(例:「対話の窓で採取。自動実行では判定が
  成り立たないため該当なし」)
- **「あり」なのに試験名を書けないものは未実装である。** 試験を書く。書けない事情
  (期待値が仕様から導けない等)なら推測で埋めずミニインタビューへ戻る
- **ADR に残した決定のうち、外から観測できるものは対応する試験を持つ。** 決定だけあって
  試験が無い状態は、この表のどこかのカテゴリが「なし」で素通りしたサインとして扱う

この表があると、後日のバグ調査や仕様書生成のときに「見ていないのか、見た上で外したのか」が
判別できる。無記録で飛ばすと、両者が同じ見た目になって漏れが発見されない。

## 試験の実在と検出力の下限を機械で確かめる

表を書き終えたら、同梱の静的検査を**必ず実行**し、結果を記録の表の直後に貼る:

```
python "<プラグインのルート>/scripts/rally_test_audit.py" --root .
```

(プラグインのルートは `${CLAUDE_PLUGIN_ROOT}`。見つからなければ `rally_test_audit.py` を
探して実行する。)検査は 4 つ — (1) 表に書いたテスト名が `tests/` に実在するか、
(2) assert も例外期待も持たない test 関数、(3) 理由の無い skip、(4) 例外の握り潰し
(`except: pass`・空の catch)。

- (1) は必ず 0 件にする。名前の書き間違いも「創作した試験」と区別がつかない
- (2)〜(4) は**下限**の検査で、指摘がそのまま不合格ではない。残す場合は指摘ごとに
  理由を記録に書く(「stdout の再設定失敗は無視してよい」など)。理由が書けない指摘は直す
- この検査は試験が**要件を検証しているか**までは見ない。それを見る手は 3 つある:
  green になった後に**確定 Gherkin ごとに実装を 1 か所壊して red になるのを確認**してから
  戻す(部分ミューテーションテスト。壊す場所は自分で選ぶので、証拠は壊したその場所について
  だけである)。カテゴリ 7 の不変条件を生成入力で検査すること。カテゴリ 11 の「下ごしらえが
  本体を通っている」ことの検査(いずれも `test-battery.md` 参照)

## green の後に壊して確かめる(部分ミューテーションテスト)

確かめたいのは、**確定 Gherkin を守る E2E が、それぞれ担当する実装を見ていること**である。
E2E が全部通ったら、確定 Gherkin ごとに、それに対応する実装を 1 か所だけ壊して(比較の向き、
並び順、境界の `<` と `<=` など)その Gherkin の E2E が red になるのを見てから戻す。壊すたびに
回すのは対応する試験だけでよい。red にならなければ、その試験は実装を見ていない(件数だけ
数えている等)ので直す。Gherkin ごとに、どこを壊して何が red になったかを記録に 1 行残す。
**書式は表で、1 行に Gherkin 1 本**(`| Gherkin | 壊した所 | red になった試験 |`)。後から足した
Gherkin や、やり直した分も同じ表に行を足す。「48 か所すべて red」のように文章でまとめると、
どの Gherkin をどの試験が守っているかの対応が記録から読めなくなる。

完了の報告の後に確定 Gherkin が増えたとき、または壊した箇所の実装を直したときは、その分を
やり直して記録に足し、**次の報告の「変えたこと」に追加分の結果を載せる**(記録にだけ足すと、
相手は最初の報告の本数のまま完了したと受け取る)。

バッテリー側の試験は対象にしない(下ごしらえが本体を通っていることはカテゴリ 11 で確かめる)。
多数の箇所を自動で壊す全量のミューテーションテストは行わない(壊すたびに試験全体を回すので
時間がかかり、振る舞いの変わらない変異の見極めを利用者に回すことになるため)。

## 部分ミューテーションテストの後に、盲検レビューを通す

部分ミューテーションテストまで済んだら、完了の報告の前に、実装の経緯を知らない
サブエージェントに仕様記録と実装を突き合わせさせる(`blind-review.md`)。
渡すのはインタビュー記録・E2E・差分・ADR・観点表と試験バッテリーのパスで、実装中の会話は
渡さない(ADR は仕様と食い違う決定を探す対象、観点表と試験バッテリーは実装と試験が従って
いるかを見る物差しとして渡す)。
レビューは一時フォルダに作ったプロジェクトの写しの上で行わせ、**返ってくるまで本物の実装と
試験を書き換えない**(途中で変わると、どの状態を見た指摘か分からなくなる)。
サブエージェントを起動できない環境では行わず、記録に「盲検レビュー: 起動できず未実施」と書く。

返ってきた指摘のうち、仕様から正しい振る舞いが導けるものは promote-bug スキルで
(複数なら再現試験を全件書いて失敗を確かめてから原因ごとに)直し、導けないものは
ミニインタビューに回す。結果は記録の「盲検レビュー結果」に残し、
完了の報告の「変えたこと」に件数と対応を 1 行で載せる。

## 実装完了の報告


完了の定義(上記)が揃ったら、報告を次の 3 見出しで、**この順に**書く。読み手は
スマホから開いて最初の数行しか見ないことがあるので、相手がすることを先頭に置く:

```markdown
## あなた待ち
最初にやること: P1「一覧が見やすい」— 下に貼った `todo list` の出力を見て、1 行 1 件で桁が揃っているか答えてください
- P2 …(人間プローブ計画の残り。P1 から順に、「見て判断すること」を問いの形で)
- 保留: …(未解決の保留。判定手段が未定(C)のまま実装に入った項目もここ)

## 変えたこと
- 実装したもの、E2E n 本 green、バッテリー 11 行記入済み、静的検査 (1) 0 件、部分ミューテーションテスト: 確定 Gherkin n 本すべて red を確認、盲検レビュー: 指摘 n 件(直した n・聞いた n・誤り n)…

## 見つけたこと
- 委任枠で仮決めした点、実装中に気づいた観点漏れ候補、ADR に残した決定
```

- 「あなた待ち」の 1 行目は、相手が**その場で**できる 1 つの行動にする(何を見て、何を答えるか)。
  P1 の「見せるもの」はこの報告に添えて出す(相手が見られる経路で。下記)
- 相手に頼むことが何も無いなら「あなた待ち: なし」と書く(見出しは省かない)
- 「変えたこと」「見つけたこと」は、あなた待ちを読んだ後に必要な人だけが読む前提で短くてよい
- 「変えたこと」の「E2E n 本 green」は、**この報告の直前に実際に流した結果**で書き、
  実行したコマンドと結果の要約(通った件数・失敗 0)を添える(例:`pytest tests -q` → `42 passed`)。
  「通るはず」「確認済み」とだけ書かない。失敗が 1 件でも残るなら完了の定義を満たしていないので、
  完了の報告にせず、残った失敗(試験名と症状)を残件として報告する
