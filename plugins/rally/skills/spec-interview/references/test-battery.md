# 標準試験バッテリー

実装フェーズで**ユーザーに確認せず自動で**展開する機械的試験のカテゴリ表。
インタビューの観点表(checklist.md)が「仕様を確定させる質問」を作るのに対し、
この表は「確定した仕様の周辺を機械的に固める試験」を作る。

## 使い方

- 実装と同時に、対象に該当するカテゴリを選んで E2E(または単体)に展開する。
  全カテゴリ必須ではない — 対象に存在しない概念(永続化しないツールに破損ファイル試験等)は飛ばしてよい
- **飛ばすときは黙って飛ばさない。** 11 カテゴリすべてについて「展開した試験名」か
  「該当なしと判断した理由」のどちらかを必ず書き、適用結果表としてインタビュー記録に残す
  (書式は spec-interview SKILL.md の「バッテリー適用結果を記録に残す」)。
  無記録で飛ばしたカテゴリは、後から見て**「該当なしと判断した」のか「そもそも見ていない」のか
  を区別できない**。この区別がつかないことが漏れの温床になる
- 試験値は仕様の具体例に合わせる(抽象的な「大きい値」でなく「999999999999999999999」)
- ここにある試験で見つかる問題を人間に触らせて発見させない。人間の役割は
  仕様の解釈ズレ・使い心地という機械化できない反例に限る

## カテゴリ

### 1. 境界値
- 0 件・1 件・ちょうど上限・上限+1
- 期間の端(月末/月初の帰属、年またぎ、うるう年 2/29、平年の 2/29 拒否)
- しきい値ぴったり(予算ちょうど、制限値ちょうど — 超過扱いかを仕様で確認して固定)

### 2. 入力異常系
- 空・空白のみ・null 相当
- 型違い(数値欄に文字)、形式違反(日付 2026-13-01、ゼロ埋めなし 2026-7)
- 過大(桁あふれ級の数値、極端に長い文字列)
- 負数・ゼロ(仕様上の扱いを固定)
- 非 ASCII(日本語・絵文字)と改行・制御文字の混入
- **弾く試験と対で「通すべき正常入力の広さ」も固定する。** 仕様が制限していない文字種・
  形式を実装のバリデーションが勝手に狭めていないか(識別子・名前・ID に非 ASCII を
  許すか等)。異常系だけを試験すると、正当な入力を弾く制限が素通りする

### 3. データ永続化の頑健性
- パース不能ファイル(途中で切れた JSON 等)
- **有効だが構造違反**(スキーマ違いの JSON: 型違い・キー欠落・空オブジェクト・リスト)
- 空ファイル(0 バイト)
- 保存先パスの異常(存在しないディレクトリ、ディレクトリを指定)
- **入力パスと出力パスの同一・包含関係**(削除・クリーン等の破壊的処理が入力データを
  巻き込まないか。同一/祖先/子孫のケースを試験し、拒否して何も消さないことを確認)
- 出力先の異常(既存の通常ファイルを出力先に指定、出力先内の読み取り専用ファイル。
  いずれも traceback でなく 1 行エラーで止まること)
- **生成物と入力の名前衝突**(自動生成ファイルと同名の入力があるとき、黙って上書きしない)

### 4. 冪等性・二重実行
- 同じ操作の再実行(二重 done、二重登録)が仕様どおりか(エラー or 冪等)

### 5. 状態遷移の違反
- 存在しない対象への操作、削除済み・完了済みへの再操作
- 順序違反(前提が満たされていない状態での操作)

### 6. 往復一致(ラウンドトリップ)
- 保存→読込→再保存で内容が変わらない
- 表示→(仕様上可能なら)再入力で同じ状態になる

### 7. 不変条件
- エラー終了後にデータファイルが変化していない(before/after 比較)
- 集計の整合(内訳の和=合計)
- 一意性(ID の重複なし・再利用なし)
- **列挙した値ではなく性質で書ける不変条件は、生成入力で検査する**(property-based testing:
  Python なら hypothesis、JS なら fast-check 等。「任意の入力 s に対し、受理されたなら保存先は
  ルートの内側」「並べ替え結果は元と同じ多重集合」)。列挙試験は列挙した N 件しか守らない。
  判定手段の割り当てで **A-サンプル**(列挙でしか書けていない A)と印が付いた項目は、
  ここで性質に書き直せないかを必ず検討し、書き直せないなら理由を表に書く
- **本体コードにも不変条件を assert として置く**(試験入力だけでなく本番の全入力で検査される。
  否定形の要件「〜を受け付けない」「〜の外に出ない」に最も効く)。試験はその assert が
  発火する入力を 1 件持つ

### 8. 出力契約
- exit code: 成功 0 / 失敗 非 0
- エラーは stderr、正常出力は stdout
- 表示崩れ(巨大値・長い文字列・空一覧)でフォーマットが破綻しない
- **座標で組む出力(図・レイアウト)は、見た目を目視でなく幾何で判定する**:要素どうしの
  重なり、線が図形を貫く、枠からのはみ出し。「読めること」を人の目に委ねると、入力の
  組み合わせ次第で崩れる経路が試験から丸ごと抜ける。入力を総当たりして 1 件も出ないことまで見る

### 9. 環境依存
- 出力エンコーディング(Windows cp932 環境での非 ASCII 出力)
- **試験自体の環境非依存性**:子プロセスを起動する試験は、子の入出力エンコーディングを
  env(PYTHONIOENCODING / PYTHONUTF8 等)で明示固定する。親側のデコード指定だけでは
  子の出力エンコーディングは変わらず、環境によって試験結果が変わる
- **試験の実行条件と本番の差**:試験だけが使う短い一時パス・書き込み先を逃がす環境変数・
  偽の時計・縮めたサンプルは、本番で壊れる条件そのものを避けて走っていることがある。
  OS の上限(パス長)・許可要求・OS が持つ時刻・実寸の件数に触れる対象は、本番と同じ置き場・
  同じ経路で動く試験を最低 1 本置く
- 「今日」に依存する処理(日付省略時の既定値)が試験で固定できる作りか
- タイムゾーン・ロケールに依存する処理があれば境界を確認
- **任意依存・環境で挙動が分岐する機能は、両方の枝に試験を書く**(有り→変換する/
  無し→そのままコピー+警告、のどちらも仕様である)。片方の枝しか走らない試験
  (`importorskip` で丸ごと skip、依存が無いと検証対象の動作自体が起きず素通り pass)は
  検出力ゼロになる。依存が有る環境でも「無いふり」を強制する手段(import の差し替え・
  環境変数)を用意し、**バグの回帰試験は必ず既定環境で red になり得る枝に置く**。
  全組み合わせ(2^n 構成)は不要——各分岐の両枝が 1 回ずつ走れば「未実行の枝」は捕まる。
  分岐同士が干渉する(A の有無で B の挙動が変わる)と分かった組だけ組み合わせを足す

### 10. スケール smoke(必要な対象のみ)
- 現実的な最大件数(例: 1 万件)で主要操作が現実的な時間・表示で完了する

### 11. 試験そのものの検出力(対象でなく試験を点検する)
- **下ごしらえが本体を通っていることを、1 件でよいので明示的に検査する**。前提を満たさない
  下ごしらえ(本体が処理対象外と判定する入力)を与えた試験は、本体を一度も通らないまま
  pass する。「対象として扱われた」ことを表す出力・状態を 1 つ決めて、そこを検査に入れる。
  下ごしらえが正しいことは、試験が緑であることからは分からない
- **測る性質が、その実行経路に存在するか**。人が読んで分かるか・対話でどう見えるかを測る
  試験は、出力を人が読まない経路(自動実行、ログだけが残る経路)で採ると判定そのものが
  成り立たない。性質が存在する経路で採り直すまで、その試験は何も測っていない

## 育て方

人間のプローブや後日のバグで「バッテリーに無いカテゴリ」が見つかったら、
一般形に蒸留してこの表へ追記する(checklist.md と同じ規律:
プロジェクト名・日付・経緯は書かない)。
