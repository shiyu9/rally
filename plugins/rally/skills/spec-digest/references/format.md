# 仕様原稿の書式

仕様書の正は `docs/spec.html`。**モデルが書くのは中身だけ**で、HTML は 1 バイトも
`scripts/spec_build.py` が持つ。章立て・列構成・記号・配色・目次・検索は原稿によって
ぶれない。目次・件数・判定・図の番号を手で書いてはならない。

```
docs/.spec-src.md（モデルが書く行形式の原稿）
        │  python ${CLAUDE_SKILL_DIR}/scripts/spec_build.py --src docs/.spec-src.md --out docs/spec.html
        ▼
docs/spec.html（完成品）
```

書き方は 2 つだけ。**キーと値は `キー: 値`、表の行は `|` 区切り。**

書式に合わない行があるとビルドが止まり、既存の `spec.html` は上書きされない。

## 章立て(固定)

| 章 | 章名 | 原稿に書くか |
|---|---|---|
| 1 | 文書情報 | 書く |
| 2 | 用語定義 | 書く |
| 3 | システム概要 | 書く(3.1 概要 / 3.2 適用場面) |
| 4 | システム構成 | 書く(4.1 構成要素 / 4.2 要素間の関係 / 4.3 動作環境) |
| 5 | インターフェース仕様 | 書く(5.1 外部との境界 / 5.2 経路ごとの仕様) |
| 6 | データ仕様 | 書く |
| 7 | 機能一覧 | **書かない(自動生成)** |
| 8 | 機能仕様 | 書く |
| 9 | エラー仕様 | 書く |
| 10 | 非機能要件 | 書く |
| 11 | 適用範囲外 | 書く |
| 12 | 設計判断 | 書く |
| 13 | 仕様の確定状況 | **書かない(自動生成)** |
| 14 | 未確定事項 | 書く |

第 7 章と第 13 章は、第 8 章の機能仕様と 3.2 の処理の流れ、各章の検証欄から機械的に
作られる。**同じ数字を 2 か所に書く場所は無い。**

章名・節名は固定で、1 文字でも違うとビルドが止まる。節名は特定のシステム形状に
寄せていない(「コマンドライン」ではなく「起動と操作」)。CLI でも GUI アプリでも
ライブラリでも、同じ節名で書ける。

## 全体の形

```
題名: mdsite 仕様書
対象: Markdown フォルダを HTML サイトに変換する CLI ツール
生成元: tests/e2e/（26 件）・docs/adr.md（8 件）

## 1 文書情報
@def
文書名: mdsite 仕様書
扱い: 生成物。手で編集しない

## 2 用語定義
@def
メモ: 変換元の Markdown ファイル

## 3 システム概要

### 3.1 概要
@p …
```

先頭の `題名` `対象` `生成元` は必須。章見出しは `## <番号> <章名>`、
節見出しは `### <番号> <節名>`。

## 指示の一覧

| 指示 | 用途 | 中身の書き方 |
|---|---|---|
| `@p` | 段落 | 指示と同じ行に本文 |
| `@def` | 定義表(項目｜内容) | `キー: 値` |
| `@table 列1 \| 列2 …` | 自由列の表 | `値1 \| 値2 …` |
| `@code` … `@end` | コード | そのまま |
| `@io` | 外部との境界図と経路ごとの仕様(5.1 / 5.2) | 後述 |
| `@path` | 1 本の経路の中身 | `@io` の各行の直下に `キー: 値` |
| `@paths` | 経路ごとの仕様の差し込み(5.2) | 中身は書かない |
| `@purpose` | 目的の見出し(3.2) | 指示と同じ行に `P-01 <目的名>` |
| `@flow` | 処理の流れ(3.2) | 後述 |
| `@graph` | 要素間の関係図(4.2) | 後述 |
| `@store` | データの入れ物(6) | 指示と同じ行に `<名前> \| <保管場所>` |
| `@schema` | 入れ物の項目表(6) | 後述 |
| `@spec` | 機能仕様ブロック(8) | 後述 |
| `@rows` | ID 付き条項表(9〜12・14) | 後述 |
| `@caption` | 直前の図の脚注 | 指示と同じ行に本文 |

章ごとに使える指示は決まっている。使えない指示を書くとビルドが止まり、その章で
使えるものを教える。

## 文中の記法

- `` `…` `` はコード。`<` `>` `&` は自動でエスケープされるので、そのまま書いてよい
- `**…**` は強調
- `F-01` `E-03` `N-02` `X-04` `D-06` `U-01` は**自動でリンクになる**。手で書かない
- **図の中では装飾が効かない。** 工程名や要素名はそのままの文字として描かれる
  (SVG は HTML のタグを持てない)。機能 ID は `| F-01` で添えるとリンクになる

## 3.1 概要 — 最初に全体像を書く

読み手が数行で「何のシステムか」をつかめるようにする。**後続の章と重複してよい。**

```
### 3.1 概要
@p mdsite は、手元の Markdown メモをブラウザで読める形にまとめて配る CLI ツールである。
@p **できること。** 入力フォルダ配下の `.md` を再帰的に集めて HTML に変換し、目次を添える。
@p **やらないこと。** 編集機能・プレビュー・全文検索は持たない。設定も履歴も残さない。
@p 詳しい範囲は第 11 章、決定の理由は第 12 章に分けて書く。
```

段落の型は **何をするものか → できること → やらないこと**。

## @io — 外部との境界と経路ごとの仕様(5.1 / 5.2)

**このシステムが外部の誰と何をやり取りするかを書く。** 相手の数も向きもシステムが
決める。決まった段組みは無い。**やり取り 1 本ごとに、その中身を `@path` でぶら下げる。**
5.1 の図と 5.2 の仕様は、どちらもこの 1 か所から作られる。

```
@io
@self mdsite | CLI
利用者 <-> 実行の指示 / 進行と結果の表示
@path 受信
内容: 入力フォルダのパス、出力フォルダのパス
手段: コマンドライン引数
形式: `python src/mdsite.py --input <入力フォルダ> --output <出力フォルダ>`。どちらも必須
契機: プロセスの起動時に 1 回
用途: パスの妥当性を検証し、収集の起点にする（F-02）
エラー: E-02 E-03 — 何も書かずに終了コード 1 で終わる
検証: test_path_same_errors
@path 送信
内容: 処理結果の要約と、エラーの理由
手段: 標準出力・標準エラー出力（どちらも UTF-8）と終了コード
形式: 正常時は標準出力に要約、異常時は標準エラーに 1 行。終了コードは 0 か 1
契機: 処理の完了時。中止の場合はその判断時
用途: 利用者が結果と、失敗した場合の原因を知る
エラー: なし
検証: test_zero_md_is_error
入力フォルダ notes/ -> .md ファイルと付随ファイル
@path 受信
…（同じ 7 項目）
@caption 入力フォルダは読み取りのみで変更しない（N-01）。
```

- `@self` はこのシステム自身。`|` の後ろは補足(省略可)
- 相手は 1 行 1 つ。向きは 3 種:
  - `相手 -> 受け取るもの`(外部から入ってくる)
  - `相手 <- 渡すもの`(外部へ出ていく)
  - `相手 <-> 受け取るもの / 渡すもの`(往復する)
- **一方向の変換だけを前提にしない。** 双方向に同期するもの、相手が 3 つ以上あるもの、
  画面で利用者と往復するものは、そのとおりに書く
- ここに書くのは**外部の相手だけ**。内部の部品は 4.2 の役目

### @path — 1 本の経路の中身

やり取りの行の**直下**に置く。`->` は `@path 受信` を 1 つ、`<-` は `@path 送信` を 1 つ、
`<->` は `@path 受信` と `@path 送信` をこの順で 2 つ書く。数や順序が合わなければビルドが止まる。

- **経路の ID(`I-01`…)は書かない。** 並び順と向きから機械が振り、図のラベルにも前置される。
  同じ番号を 2 か所に書かせない
- **相手と向きも書かない。** 上のやり取り行から入る
- 項目は 7 つ。該当が無くても `なし` と書いて項目を残す

| 項目 | 何を書くか |
|---|---|
| `内容` | **やり取りされるデータそのもの。** 名詞で書く(「入力フォルダのパス」) |
| `手段` | どうやって運ばれるか(コマンドライン引数 / 標準出力 / ファイルの読み書き / Web API / 画面の操作) |
| `形式` | その表現と約束事(引数の書式・出力の行数・ファイル形式・終了コード) |
| `契機` | いつ発生するか(起動時に 1 回 / 操作のたび / 完了時) |
| `用途` | 受け取って何をするか。送る側は相手が何をするか。`F-nn` で機能に繋ぐ |
| `エラー` | この経路が失敗したときどうなるか。`E-nn` でエラー仕様に繋ぐ |
| `検証` | この記述を固定しているテスト名。`@spec` と同じ書き方 |

**`内容` `形式` `用途` は混ざりやすい。** 「何のための指定か」は `内容` ではなく `用途` に書く。
`内容` に目的を書くと `用途` と同じことを 2 回書くことになる。

## @paths — 経路ごとの仕様(5.2)

5.2 に `@paths` とだけ書く。`@io` に書いた経路が、第 8 章の機能仕様と同じブロック形式で
並ぶ。中身は `@io` が持つので、ここには何も書かない。

## @purpose — 目的(3.2)

**このシステムを何のために使うかを、目的ごとに区切って書く。** 3.2 の流れはこの目的を
1 つずつ受け持ち、目的の説明の直下に図が出る。

```
@purpose P-01 手元の Markdown メモを、ブラウザで読める形にまとめて配る
@p フォルダごと HTML に変換し、目次から辿れる状態にする。編集は対象外。
@flow P-01
…
@caption …
```

- ID は `P-01` から連番
- 目的を定義したら、**対応する流れを必ず書く**(無ければビルドが止まる)
- 中身は文章(`@p`)で書く。表にしない

## @flow — 処理の流れ(3.2)

**流れは目的ごとに 1 つ。** 見出しで目的を指す。

```
@flow P-01
端子 アプリを開く
工程 端末の前提を確かめる | F-01
判断 保存されたトークンがあるか？
枝 いいえ
  工程 ログイン画面へ送る
  終了 ログインするまで扱えない
枝 はい
工程 保存トークンでログイン状態に戻す | F-02
例外 トークンを復号できない | E-06
  工程 再ログインを求める
  終了 ログインするまで扱えない
例外終わり
並行
経路
  工程 前回済んでいない同期を片付ける | F-03
経路
  工程 新譜を探す | F-04
合流
端子 箱一覧を扱える
@caption 前提を満たさない項目があっても止めない。断り書きを添えるだけ。
```

| 語 | 意味 | 図での形 |
|---|---|---|
| `端子` | 開始・正常終了 | 角丸 |
| `工程` | 処理。`\| F-01` でその機能に紐づく | 角箱＋番号 |
| `判断` `枝 <ラベル>` | 排他分岐。2 度目の `枝` で本線に戻る | 菱形 |
| `終了` | 異常終了 | 太枠の角丸 |
| `待機 <条件>` | 時間や状態を待つ | 琥珀色の箱 |
| `繰り返し <条件>` … `繰り返し終わり` | 前判定(while) | 破線の枠。条件は上 |
| `繰り返し` … `繰り返し終わり <条件>` | 後判定(do-while) | 破線の枠。条件は下 |
| `例外 <条件> \| E-nn` … `例外終わり` | 直前の工程から離脱する | 破線で抜ける |
| `並行` `経路` … `合流` | 同時に走り、全部の完了を待つ | 太いバーで挟む |
| `順不同` `経路` … `順不同終わり` | 逐次だが順序は決まっていない | 淡いバーで挟む |

- 工程には自動で `01` から番号が振られる。**目的ごとに振り直す**。第 7 章には
  `P-01:03`(目的 P-01 の 3 番目の工程)の形で出る
- **端子と分岐の中身には番号を振らない。** 繰り返し・並行の中は本線として番号を持つ
- 第 7 章の「工程」列はここから作られる。**第 8 章の全機能が、いずれかの流れの工程に
  現れること**(どの流れにも現れない機能があるとビルドが止まる)。1 つの機能が複数の
  流れに現れてよい

書けない組み合わせ:

- 分岐(`枝`)の中に `並行` `順不同` `繰り返し` `例外` は書けない
- 繰り返しの中に `判断` は書けない
- 分岐の中の工程に機能 ID は添えられない(番号を持たないため)
- `例外` は `工程` か `待機` の直後にだけ置ける
- `並行` `順不同` の直後は `経路`。経路は 2 つ以上必要

## @graph — 要素間の関係(4.2)

**4.1 に挙げた構成要素どうしと、外部との関係を書く。** 静的な関係だけで、時系列は
3.2 の役目。

```
@graph
@hub domain | 端末にも Spotify にも依存しない中核
app（画面） -> domain: 箱とアーティストの操作
domain -> app（画面）: 箱の中身と同期の状況
app（Spotify） -> Spotify Web API: 検索・取得・読み書き
利用者 -> app（画面）: 箱とアーティストの操作
@caption 矢印は関係の向きを表す。
```

- 関係は `源 -> 先: ラベル` の 1 行 1 本。**中心を通らない関係も書ける**
- 同じ 2 要素の往復は 1 本の双方向の辺にまとまる
- `@hub` は強調したい要素(任意)。指定しなくても図になる
- **配置は自動で決まる。** 辺の交差が最も少なく、線が短くなる並びを探す。位置は書かない
- **辺は結ぶ 2 つ以外の箱を貫かない。** 貫通は交差より重く扱って配置で避け、それでも
  避けきれない組は箱をよけて 1 か所で折れる。要素の上を線が走ることは無い
- **4.1 に挙げた要素はすべてここに現れること**(現れないとビルドが止まる)

## @store / @schema — データ仕様(6)

**データの入れ物ごとにセクションを作る。** テーブルや JSON の単位で分ける。

```
@store 箱 | 端末のデータベース（Room）
@p 利用者が作る入れ物。1 行が 1 つの箱で、非公開プレイリスト 1 つと対応する。
@schema
箱 ID | 文字列 | 36 | 36 | 文字 | ○ | - | - | 箱の識別子（UUID）
名前 | 文字列 | 1 | 200 | 文字 | - | - | - | 利用者が付ける名前。空は不可（E-01）
作成時刻 | 整数 | - | - | エポックミリ秒 | - | - | - | 作成した時点
```

`@schema` は 9 列で固定:

| 列 | 書き方 |
|---|---|
| データ名 | 項目の名前 |
| 型 | 文字列・整数・真偽 など |
| 下限値 / 上限値 | 数値。無ければ `-` |
| 単位 | 文字・バイト・件・エポックミリ秒 など。無ければ `-` |
| 主キー | `○` か `-` |
| 外部キー | `○` か `-` |
| 参照先 | 参照する入れ物の名前。複数なら `箱, カタログ`。無ければ `-` |
| 説明 | 何を入れるか |

- 外部キーが `○` なら参照先が必須。`-` なら参照先も `-`
- **参照先は `@store` で定義した入れ物の名前**(無い名前を書くとビルドが止まる)
- 参照先の末尾に `+` を付けると「親 1 つにつき子が 1 件以上」。既定は 0 件以上
  (親を作った直後は子が無いのがふつう)

**6 章の先頭には ER 図が自動で入る。** 関係は原稿に書かない。`@schema` の外部キーが
唯一の出どころで、図と表が食い違わない。IE 記法で描き、参照される側が「1」、
参照する側が「0 以上」(`+` を付けたときだけ「1 以上」)。

## @spec — 機能仕様(第 8 章)

```
@spec F-01 出力初期化 | 確定
概要: 書き出し前に出力フォルダの中身を全削除する
実行契機: 実行前検証の完了直後、書き出し処理の前
前提条件: 9 章の判定条件すべてに該当しないこと（N-02）
入力: 出力フォルダ
処理: 出力フォルダ配下の全ファイル・全フォルダを削除する
出力: 空の出力フォルダ
エラー: E-07 — 削除できないファイルが存在する場合、中止する
検証: test_output_is_wiped test_idempotent
```

- 見出しは `@spec <ID> <機能名> | <確定状況>`。確定状況は **確定 / 暫定 / 未固定**
- **ID は処理の流れの順に `F-01` から連番。** 話題順ではない
- `概要` `実行契機` `入力` `出力` `検証` は必須。該当が無くても `なし` と書いて項目を残す
- `前提条件` `処理` `エラー` は省略可(省略すると「なし」になる)
- 同じ項目を複数行書くと箇条書きになる。`処理` は書いた順の番号付きになる
- **工程番号は書かない。** 3.2 の流れに `| F-01` を添えることで対応づく

### 検証欄の書き方

| 書き方 | 意味 | 判定 |
|---|---|---|
| `test_a test_b` | 人が決めて E2E で固定した | 確定 |
| `? test_a` | 現状を観測して固定しただけ(特性化テスト) | 暫定 |
| `なし` | 決定はあるが試験が無い | 未固定 |

テスト名は識別子として妥当なら何でもよい(日本語のテスト名も書ける)。

**推測で `確定` を書かない。** 人が確認していない振る舞いは `?` を付ける。ここが
第 13 章の内訳になり、仕様書のどこが脆いかの地図になる。

## @rows — ID 付き条項表

列は章が決める。モデルは行だけを書く。ID は各章で `01` から連番。

| 章 | 列 |
|---|---|
| 9 エラー仕様 | `E-nn \| 判定条件 \| メッセージ内容 \| 流れ \| 検証` |
| 10 非機能要件 | `N-nn \| 分類 \| 条件 \| 検証` |
| 11 適用範囲外 | `X-nn \| 対象外の事項 \| 理由` |
| 12 設計判断 | `D-nn \| 決定 \| 理由` |
| 14 未確定事項 | `U-nn \| 項目 \| 現在の動作 \| 確定に必要な確認事項` |

検証欄の書き方は `@spec` と同じ。判定は自動で付く。

### 9 章の「流れ」列

**そのエラーが 3.2 のどこで起きるかを書く。**

- 流れが変わるもの(そこから離脱する・別の経路に入る)は、3.2 の工程に
  `例外 <条件> | E-nn` を添えたうえで、この列にどの流れかを書く
  (例: `P-04 の書き込みから離脱`)
- 流れが変わらないもの(その操作が失敗するだけで、次に進む道筋は同じ)は
  **`流れ不変`** と書く

空欄にはできない。書いていないと、**見ていないのか、見た上で描かないと決めたのかが
区別できない**。第 8 章の機能が「どの流れにも現れないとビルドが止まる」のと同じ規律を、
エラーにも効かせる。

この列に流れを書いたのに 3.2 に `例外` が無ければビルドが止まる。

## 書いてよいこと・いけないこと

- 第 8 章・9 章・10 章に書けるのは、E2E に対応する試験があるものだけ。試験が無いものは
  `なし` と書いて `未固定` にするか、第 14 章へ移す
- 第 2 章・11 章・12 章は試験に対応しなくてよい(用語・スコープ外・設計判断は試験の
  対象ではない)
- 第 12 章は決定と理由を 1 行ずつ。ADR 全件ではなく、利用者の理解に効くものだけ
- 形容詞で逃げない。「壊れない」ではなく「書き込み・削除・属性変更を行わない」と書く
