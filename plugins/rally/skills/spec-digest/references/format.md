# 仕様原稿の書式

仕様書の正は `docs/spec.html`。**モデルが書くのは中身だけ**で、HTML は 1 バイトも
`scripts/spec_build.py` が持つ。章立て・列構成・記号・配色・目次・検索は原稿によって
ぶれない。目次・件数・判定・図の番号を手で書いてはならない。

```
docs/.spec-src.md（モデルが書く行形式の原稿）
        │  python ${CLAUDE_SKILL_DIR}/scripts/spec_build.py --src docs/.spec-src.md --out docs/spec.html
        ▼
docs/spec.html（完成品）
```

書き方は 2 つだけ。**キーと値は `キー: 値`、表の行は `|` 区切り。**

## 章立て(固定)

| 章 | 章名 | 原稿に書くか |
|---|---|---|
| 1 | 文書情報 | 書く |
| 2 | システム概要 | 書く(2.1 入出力 / 2.2 適用場面) |
| 3 | システム構成 | 書く(3.1 構成要素 / 3.2 要素間の関係 / 3.3 処理の流れ / 3.4 動作環境) |
| 4 | インターフェース仕様 | 書く(4.1 コマンドライン / 4.2 標準出力・終了コード / 4.3 生成する HTML の構造) |
| 5 | データ仕様 | 書く |
| 6 | 機能一覧 | **書かない(自動生成)** |
| 7 | 機能仕様 | 書く |
| 8 | エラー仕様 | 書く |
| 9 | 非機能要件 | 書く |
| 10 | 適用範囲外 | 書く |
| 11 | 設計判断 | 書く |
| 12 | 仕様の確定状況 | **書かない(自動生成)** |
| 13 | 未確定事項 | 書く |
| 14 | 用語定義 | 書く |

第 6 章と第 12 章は、第 7 章の機能仕様と 3.3 の処理の流れ、各章の検証欄から機械的に作られる。
**同じ数字を 2 か所に書く場所は無い。**

## 全体の形

```
題名: mdsite 仕様書
対象: Markdown フォルダを HTML サイトに変換する CLI ツール
生成元: tests/e2e/（26 件）・docs/adr.md（8 件）

## 1 文書情報
@def
文書名: mdsite 仕様書
扱い: 生成物。手で編集しない

## 2 システム概要

### 2.1 入出力
@io
…
```

先頭の `題名` `対象` `生成元` は必須。章見出しは `## <番号> <章名>`、節見出しは
`### <番号> <節名>`。番号・名称は上の表のとおりで、1 文字でも違うとビルドが止まる。

## 指示の一覧

| 指示 | 用途 | 中身の書き方 |
|---|---|---|
| `@p` | 段落 | 指示と同じ行に本文 |
| `@def` | 定義表(項目｜内容) | `キー: 値` |
| `@table 列1 \| 列2 …` | 自由列の表 | `値1 \| 値2 …` |
| `@code` … `@end` | コード | そのまま |
| `@io` | 入出力の図 | `欄名: 項目 \| 項目 …` を 3 行 |
| `@graph` | 要素間の関係図 | 後述 |
| `@flow` | 処理の流れ | 後述 |
| `@spec` | 機能仕様ブロック | 後述 |
| `@rows` | ID 付き条項表 | 後述 |
| `@caption` | 直前の図の脚注 | 指示と同じ行に本文 |

章ごとに使える指示は決まっている。使えない指示を書くとビルドが止まり、その章で使えるものを教える。

## 文中の記法

- `` `…` `` はコード。`<` `>` `&` は自動でエスケープされるので、そのまま書いてよい
- `**…**` は強調
- `F-01` `E-03` `N-02` `X-04` `D-06` `U-01` は**自動でリンクになる**。手で書かない

## @spec — 機能仕様(第 7 章)

```
@spec F-01 出力初期化 | 確定
概要: 書き出し前に出力フォルダの中身を全削除する
実行契機: 実行前検証の完了直後、書き出し処理の前
前提条件: 8 章の判定条件すべてに該当しないこと（N-02）
前提条件: 出力フォルダ配下の全ファイルが削除可能であること
入力: 出力フォルダ
処理: 出力フォルダ配下の全ファイル・全フォルダを削除する
処理: 出力フォルダ自体は残す
出力: 空の出力フォルダ
エラー: E-07 — 削除できないファイルが存在する場合、中止する
検証: test_output_is_wiped test_idempotent
```

- 見出しは `@spec <ID> <機能名> | <確定状況>`。確定状況は **確定 / 暫定 / 未固定** のいずれか
- **ID は処理の流れの順に `F-01` から連番。** 話題順ではない
- `概要` `実行契機` `入力` `出力` `検証` は必須。該当が無くても `なし` と書いて項目を残す
- `前提条件` `処理` `エラー` は省略可(省略すると「なし」になる)
- 同じ項目を複数行書くと箇条書きになる。`処理` は書いた順の番号付きになる
- **工程番号は書かない。** 3.3 の処理の流れに `| F-01` を添えることで対応づく。
  番号は機械が採番するので、手で書くとずれる

### 検証欄の書き方

| 書き方 | 意味 | 判定 |
|---|---|---|
| `test_a test_b` | 人が決めて E2E で固定した | 確定 |
| `? test_a` | 現状を観測して固定しただけ(特性化テスト) | 暫定 |
| `なし` | 決定はあるが試験が無い | 未固定 |

**推測で `確定` を書かない。** 人が確認していない振る舞いは `?` を付ける。ここが
第 12 章の内訳になり、仕様書のどこが脆いかの地図になる。

## @rows — ID 付き条項表

列は章が決める。モデルは行だけを書く。ID は各章で `01` から連番。

| 章 | 列 |
|---|---|
| 8 エラー仕様 | `E-nn \| 判定条件 \| メッセージ内容 \| 検証` |
| 9 非機能要件 | `N-nn \| 分類 \| 条件 \| 検証` |
| 10 適用範囲外 | `X-nn \| 対象外の事項 \| 理由` |
| 11 設計判断 | `D-nn \| 決定 \| 理由` |
| 13 未確定事項 | `U-nn \| 項目 \| 現在の動作 \| 確定に必要な確認事項` |

検証欄の書き方は @spec と同じ。判定は自動で付く。

```
@rows
N-01 | データ保全 | 入力フォルダ配下のファイルに対し、書き込み・削除・属性変更を行わない | test_input_untouched
N-06 | 再現性 | 目次の整列順はロケール・ファイル更新時刻に依存しない | ? test_index_order_and_titles
N-07 | 文字コード | 標準出力・標準エラーの文字コードを UTF-8 に固定する | なし
```

## @io — 入出力の図(2.1)

3 行ちょうど。1 行目が入力、2 行目が処理、3 行目が出力。

```
@io
入力フォルダ: notes/ | 　index.md | 　img/cover.png
mdsite: .md を .html に変換 | 目次を生成 | 非 .md を複製
出力フォルダ: site/ | 　index.html | 　img/cover.png
@caption 入力の相対パスを保持したまま出力する。
```

## @graph — 要素間の関係(3.2)

**静的な関係だけを書く。時系列は 3.3 の役目。**

```
@graph
@hub mdsite.py | 単一スクリプト
@left 利用者
利用者 -> mdsite.py: 引数
mdsite.py -> 利用者: 標準出力・終了コード
mdsite.py -> markdown-it-py: 呼び出し
mdsite.py -> 入力フォルダ: 読み取り
mdsite.py -> 出力フォルダ: 削除・書き込み
@caption 矢印は関係の向きを表す。
```

- `@hub` は中心の要素。`|` の後ろは補足(省略可)
- `@left` は左に置く要素。中心との往復はここに集める
- 関係は `源 -> 先: ラベル` の 1 行 1 本。中心から出る辺は本数の制限なし(図が縦に伸びる)
- 各要素は 1 度だけ登場する。同じ要素を何度も書かない
- ラベルは関係の性質(`読み取り` `削除・書き込み` `呼び出し`)。順序を表す語を入れない

## @flow — 処理の流れ(3.3)

```
@flow
端子 利用者がコマンドを実行する
工程 引数を解析する
判断 実行前検証でエラーあり？
枝 はい
  工程 標準エラーに 1 行出力する
  終了 終了コード 1
枝 いいえ
工程 出力フォルダ配下を全削除する | F-01
工程 入力フォルダから対象を収集する | F-02
端子 終了コード 0
@caption 検証を通過するまで削除・書き込みは開始しない（N-02）。
```

| 語 | 意味 |
|---|---|
| `端子` | 開始・正常終了 |
| `工程` | 処理。`| F-01` でその機能に紐づく。`| F-03 F-04` と並べると、2 つ目以降は「F-03 の内部で実行される機能」になる |
| `判断` | 分岐 |
| `枝 <ラベル>` | 分岐の始まり。2 度目の `枝` で本線に戻る |
| `終了` | 異常終了 |

- 工程には自動で `01` から番号が振られる。**端子と分岐の中身には振られない**
- 第 6 章の「工程」列はここから作られる。**第 7 章の全機能が、いずれかの工程に現れること**
  (現れない機能があるとビルドが止まる)
- 分岐の中の工程は番号を持たないため、機能 ID を添えられない
- **分岐の数に制限は無い。** ただし `判断` の次の行は必ず `枝`、`枝` は 2 回
  (分岐に入る側・本線に戻る側)書く。閉じ忘れはビルドが止める

## 書いてよいこと・いけないこと

- 第 7 章・8 章・9 章に書けるのは、E2E に対応する試験があるものだけ。試験が無いものは
  `なし` と書いて `未固定` にするか、第 13 章へ移す
- 第 10 章・11 章・14 章は試験に対応しなくてよい(スコープ外・設計判断・用語は試験の対象ではない)
- 第 11 章は決定と理由を 1 行ずつ。ADR 全件ではなく、利用者の理解に効くものだけ
- 形容詞で逃げない。「壊れない」ではなく「書き込み・削除・属性変更を行わない」と書く
