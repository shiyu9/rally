# 仕様が書けるかの判定表

**仕様書が書けることは、設計が明確であることと同じである。** 書けない箇所は、
設計が決まっていない箇所か、試験で押さえていない箇所である。

仕様書の生成(spec-digest)は実装がひと区切りしてから使う道具なので、そこで不備が
出るのでは遅い。**プランを確定する前に、この表で「書けるか」を確かめる。**

## 使い方

手順 5 の整合チェックで、確定・委任した内容だけで各章が書けるかを見る。
書けない章があれば、それは設計の穴である。処理は既存の枠組みに乗せる:

| 書けない理由 | 扱い |
|---|---|
| 観測できる振る舞いが未定義 | **質問ラウンド(手順 2)へ戻す** |
| 外から見えない実装の都合 | **委任枠で仮決め**して明記する |
| 決めないと決めた | **スコープ外**として記録する |

**全項目を質問するのではない。** 答えによって設計が変わるものだけを戻す。
1 ラウンド最大 4 問の制約は変わらない。

## 判定表

### 1 文書情報 / 2 用語定義

| 書けるか | 揃っているべきもの |
|---|---|
| 何を仕様の正とするか言えるか | E2E か、実機で確かめた値か |
| 独自の言葉を定義できるか | 要望に出てきた語のうち、一般的でないもの |
| データ・状態・操作に仕様書での名前を付けられるか | 利用者の言い方 → 仕様書の用語 → 画面上の表記、の対応 |

書けないときの兆候:ユーザーと自分で同じ語を違う意味で使っている。
「箱」「タグ」「項目」のような一般語を、この文脈だけの意味で使っている。

### 3.1 概要

| 書けるか | 揃っているべきもの |
|---|---|
| 何をするものか、どんな価値があるか 1 文で言えるか | 対象の輪郭と、利用者が得るもの |
| 提供する機能を一通り挙げられるか | 機能の全体(特定の機能に偏らない。例外的な話は入れない) |
| 対象外としたものを挙げられるか | スコープ外(観点⑥で確認したもの) |

書けないときの兆候:「〜を管理するツール」以上に具体化できない。できることが
1 つしか挙がらない。やらないことが空。

### 3.2 ユースケース(目的と流れ)

| 書けるか | 揃っているべきもの |
|---|---|
| **目的を切り出せるか** | 利用者が達成したいことの単位(コマンド・画面・機能の単位ではない) |
| 目的ごとに、誰が・何に対して・何のために何をするか言えるか | 誰が・対象・概要(流れの要約ではない) |
| 目的ごとに始点と終点が言えるか | 端子(何から始まり、何で終わるか) |
| 工程の順序が決まっているか | 直列か、順不同か、並行か |
| 繰り返す箇所があるか | 条件と、判定が前か後か |
| 途中で抜ける経路があるか | 例外と、そのときのエラー ID |

**Gherkin は 1 シナリオ単位なので、流れ全体を持たない。** 個々の振る舞いが決まって
いても、それらがどの順で起きるかは別に決める必要がある。

書けないときの兆候:目的が 1 つしか出てこない(実際は起動・登録・同期などに分かれる)。
「AしてBしてC」と直列に並べたが、本当は順不同である。

### 4.1 / 4.2 構成要素とモジュール結合図

| 書けるか | 揃っているべきもの |
|---|---|
| 内部を部品に分けられるか | 部品の名前と役割 |
| 部品どうしの関係が言えるか | どちらがどちらを呼ぶか |
| 外部との接点を持つ部品が言えるか | 外部依存の局在(外部エンティティそのものは 5 章に書き、ここには描かない) |

**技術選定(手順 6)とは別物。** 「何を使うか」ではなく「どう分けるか」。
小さなツールで分割が不要なら「単一スクリプト」と 1 行で書けばよいが、
**分けないと決めたことを記録する**。

書けないときの兆候:部品が挙がらない。全部が 1 つの塊で、外部依存がどこに
入るかも決まっていない。

### 4.3 動作環境

| 書けるか | 揃っているべきもの |
|---|---|
| どこで動かすか言えるか | OS・端末・実行環境(ランタイムやブラウザ)と、そのうち実機で確かめたもの |
| 何を入れれば動くか言えるか | 必須の依存と版、その宣言の置き場所(test-battery カテゴリ 9) |
| 成果物を受け取る端末が分かっているか | 利用者が開く・使う端末と、そこで確かめる方法(B のプローブ)か未確定事項 |
| 試験だけで使うものを分けられるか | 試験の道具と、本番に要るものの区別 |

**利用者の端末は推測で埋めない(手順 1.5)。** 作る側の環境で動いたことと、利用者の
端末で使えることは別に書く。

書けないときの兆候:「たぶん動く」としか言えない。成果物を開く端末を聞いていない。
依存を入れたが宣言していない、またはこのフォルダの外(パソコン共通の環境)に入れた。

### 5.1 外部インターフェース一覧

| 書けるか | 揃っているべきもの |
|---|---|
| 外部エンティティを全部挙げられるか | 利用者・外部サービス・ファイル・DB・OS の機能 |
| 外部エンティティごとに、インターフェースを 1 対の要求と応答で挙げられるか | コマンド・エンドポイント・画面の操作・呼び出す外部 API ごとに 1 つ |
| 要求元がどちらか言えるか | 受付(外部エンティティが要求する) / 発行(このシステムが要求する) |

書けないときの兆候:「入力」「出力」としか書けない。外部エンティティが 1 つしか出てこない
(利用者を忘れていることが多い)。複数の操作を 1 つのインターフェースにまとめてしまう。

### 5.2 インターフェース詳細

**インターフェース 1 つごとに 8 項目を書く。**

| 書けるか | 揃っているべきもの |
|---|---|
| 要求として渡されるデータが言えるか | 要求。データの名前を名詞で(目的は用途へ) |
| 応答として返されるデータが言えるか | 応答。無ければ「なし」と言えるか |
| 受け渡しの方式が言えるか | 手段(引数・標準出力・ファイル・HTTP・画面の操作) |
| 表現と規約が言えるか | 形式(引数の書式・生成物の構造・終了コード・ステータスコード) |
| いつ発生するか言えるか | 契機(起動時に 1 回 / 操作のたび / 完了時) |
| 要求を受けて何を行うか言えるか | 用途。機能(F-nn)に繋がるか |
| 失敗したときの動作が言えるか | エラー(E-nn)。無ければ「なし」と言えるか |
| 対応する試験があるか | E2E の名前(無ければ未固定) |
| 要求と応答を項目の水準で言えるか | 要求パラメータごとの名前・型・必須か・既定・取りうる値、応答項目の名前と型 |

**節名は形状に寄せていない。** CLI ならコマンド、GUI なら画面の操作、ライブラリなら
関数の呼び出しが、いずれも 1 つのインターフェースとして同じ 8 項目で書ける。

書けないときの兆候:引数は決めたが、失敗したときに何を返すか決まっていない。
生成物の中身が「HTML」までしか決まっていない。往復する相手なのに、受け取る側しか
決まっていない。

### 6 データ仕様

| 書けるか | 揃っているべきもの |
|---|---|
| データストアを挙げられるか | テーブル・ファイル・JSON の単位 |
| データストアごとに保管場所が言えるか | どこに置くか |
| 項目ごとに、実装上の名前と仕様書での名前が言えるか | データ名(キー名・列名)と和名 |
| 項目ごとに型が言えるか | 実装の型の名前(`str`・`int`・`list` など) |
| 範囲と単位が言えるか | 下限・上限・単位(無ければ「無い」と言える) |
| 主キーが言えるか | 何で 1 行を識別するか |
| データストア間の参照が言えるか | 外部キーと参照先 |

**これは観点①の「永続化先」より細かい。** 保存すると決めただけでは書けない。

書けないときの兆候:「JSON で保存する」までは決まったが、何の項目を持つか
決まっていない。ID の桁数・名前の最大長が決まっていない。

### 8 機能仕様

| 書けるか | 揃っているべきもの |
|---|---|
| 機能ごとに実行契機が言えるか | いつ動くか |
| 前提条件が言えるか | 何が満たされている必要があるか |
| 入力と出力が言えるか | 受け取るもの・返すもの |
| 対応するエラーが言えるか | 失敗したときどうなるか |
| 対応する試験があるか | E2E の名前(無ければ未固定) |

書けないときの兆候:「〜する機能」とは言えるが、いつ動くかが決まっていない。
エラー時の扱いが決まっていない。

### 9 エラー仕様

| 書けるか | 揃っているべきもの |
|---|---|
| 拒否する条件が言えるか | 判定条件 |
| 何を伝えるか言えるか | メッセージの内容 |
| **流れが変わるか言えるか** | 離脱するか、その操作が失敗するだけか |
| 対応する試験があるか | E2E の名前 |

**流れが変わるかどうかを決めていないと、3.2 と繋がらない。** エラーの一覧は
あるのに、それがいつ起きるのかを読み手が自力で対応づける状態になる。

### 10 非機能要件 / 11 適用範囲外 / 12 設計判断 / 14 未確定事項

| 章 | 書けるか |
|---|---|
| 10 非機能要件 | 機能に依らず常に成り立つ条件を挙げられるか。**試験で押さえられるか** |
| 11 適用範囲外 | やらないことと、その理由が言えるか |
| 12 設計判断 | 選んだ理由と、捨てた案が言えるか |
| 14 未確定事項 | 保留したものと、確定に必要な確認事項が言えるか |

## この表を使うタイミング

- **手順 5 の整合チェック**(まとめ指示を受けたあと。プラン確定の前)
- 実装中に「ここ決まってないな」と気づいたとき(ミニインタビューへ戻る判断材料)

## 育て方

実装後に spec-digest を回して詰まった箇所があれば、**その章の判定表に項目を足す**。
「仕様書を書こうとして初めて分かった」を次から前倒しにする。
