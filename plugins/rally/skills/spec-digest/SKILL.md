# spec-digest:基本設計書としての仕様書を生成する

rally では「最新の正しい仕様」は E2E 試験コードだが、初見の人には読みにくい。
このスキルは E2E と ADR から `docs/spec.html` を導出する。単一ファイルで、ブラウザで
開くだけで読め、章の目次と全文検索が付く。

## 原則

1. **HTML を書かない。** モデルが書くのは `docs/.spec-src.md`(行形式の原稿)だけ。
   章立て・列構成・記号・配色・目次・検索は `scripts/spec_build.py` が持つ。
2. **数字を 2 か所に書かない。** 第 6 章(機能一覧)と第 12 章(仕様の確定状況)、
   表紙の件数、**工程番号**、E2E 件数、判定は**すべて自動生成**。原稿に書いてはならない。
   工程番号は 3.3 の処理の流れに `| F-01` を添えることで対応づく。
3. **書いてよいのは E2E で検証されている振る舞いだけ。** 試験が無いものは検証欄に
   `なし` と書いて「未固定」にするか、第 13 章(未確定事項)へ移す。
4. **推測で「確定」にしない。** 人が確認していない振る舞いは検証欄に `?` を付けて
   「暫定」にする。ここが第 12 章の内訳になる。
5. **spec.html は派生物。** 手で編集しない。仕様が変わったら再生成する。
   古い spec.html と E2E が食い違ったら、正は常に E2E。

## 手順

1. `tests/e2e/` を読み、検証されている振る舞いを機能別に整理する。
   **各振る舞いを固定しているテスト関数名を控える**(検証欄に使う)
2. 実装を読み、**処理の実行順**を把握する。第 7 章の機能はこの順に並べ、ID も
   `F-01` から実行順に振る。話題順にしない
3. `docs/adr.md` を読み、決定と理由を対で要約する(全件でなく、利用者の理解に効くもの)
4. `docs/interviews/` の最新記録から「スコープ外」「保留」、および
   **標準試験バッテリーの適用結果表**を拾う。「該当なし」で飛ばしたカテゴリがあれば、
   それが第 13 章の候補になる
5. `references/format.md` に従って `docs/.spec-src.md` を書く
6. ビルドする:

   ```bash
   python "${CLAUDE_SKILL_DIR}/scripts/spec_build.py" \
     --src docs/.spec-src.md --out docs/spec.html
   ```

   `${CLAUDE_SKILL_DIR}` はこのスキル自身のディレクトリに展開される(プラグインルート
   ではない)。展開されず文字列のまま残る環境では、`**/spec-digest/scripts/spec_build.py`
   を検索してそのパスを使う。
7. **失敗したら**、stderr の「N 行目: …」に従って原稿を直し、通るまで 6 を繰り返す。
   失敗時は既存の spec.html を書き換えないので、途中で壊れた仕様書が残ることはない
8. 「決定はあるが試験が無い記述が N 件あります」の注意が出たら、その N 件を確認する。
   本来は実装フェーズのバッテリー適用で見つかるべきもので、ここで出るのは前段の漏れ
9. 原稿 `docs/.spec-src.md` は残す(次回の再生成の下書きになる)。
   `.gitignore` に入れず、E2E と一緒に更新する
10. ユーザーには「`docs/spec.html` をブラウザで開いてください」と伝え、
    表紙の件数(機能・エラー・非機能要件・E2E・確定・暫定)を一言添える

## よくある詰まり

- **第 6 章・第 12 章を書いてしまう** — 原稿に書くとビルドが「章の番号・順序が違う」で
  止まる。この 2 章は自動生成
- **ID が連番でない** — 機能は実行順に `F-01` から。エラー・非機能要件なども各章で
  `01` から連番。抜けや飛びは止まる
- **`枝` の閉じ忘れ** — `枝` は分岐に入る側と本線に戻る側の 2 回書く。1 回だけだと止まる
- **機能が処理の流れに現れない** — 第 7 章の全機能が、3.3 のいずれかの工程に
  `| F-nn` として現れる必要がある。内部で実行される機能は、呼び出す工程に並べて書く
  (`| F-03 F-04`)

## 旧 `docs/spec.md` がある場合

v0.2 以前は Markdown で出力していた。同じ内容が二重に残るとどちらが正か分からなくなる。
`docs/spec.html` を生成したあと、**ユーザーに確認してから** `docs/spec.md` を削除し、
README などの参照を張り替える。

## 品質基準

- **可読性**: アプリを知らない人が spec.html だけで「何ができるか・どう使うか・
  何をするとどうなるか」を把握できる
- **整合性**: 第 7・8・9 章の検証欄のテスト名が実在するテスト関数と一致する
- **正直さ**: 人が確認していない振る舞いを「確定」にしない
