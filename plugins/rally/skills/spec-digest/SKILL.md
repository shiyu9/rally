# spec-digest:基本設計書としての仕様書を生成する

rally では「最新の正しい仕様」は E2E 試験コードだが、初見の人には読みにくい。また、E2E は
「何ができるか」を固定するが、「コードのどこにあるか」「ソースにだけある事実は何か」は教えない。
仕様書は、使う人のための層(何ができるか)と、保守する人のための層(どこにあるか)を 1 つにまとめる。
このスキルは E2E と ADR から `docs/spec.html`(本体)と `docs/spec-flow.html`(別紙「処理の流れ」)を導出する。単一ファイルで、ブラウザで
開くだけで読め、章の目次と全文検索が付く。

## 原則

1. **HTML を書かない。** モデルが書くのは `docs/.spec-src.md`(行形式の原稿)だけ。
   章立て・列構成・記号・配色・目次・検索は `scripts/spec_build.py` が持つ。
2. **数字を 2 か所に書かない。** 第 7 章(機能一覧)と第 13 章(仕様の確定状況)、
   表紙の件数、**工程番号**、E2E 件数、判定は**すべて自動生成**。原稿に書いてはならない。
   工程番号は 3.2 の処理の流れに `| F-01` を添えることで対応づく。
3. **書いてよいのは E2E で検証されている振る舞いだけ。** 試験が無いものは検証欄に
   `なし` と書いて「未固定」にするか、第 14 章(未確定事項)へ移す。
4. **推測で「確定」にしない。** 人が確認していない振る舞いは検証欄に `?` を付けて
   「暫定」にする。ここが第 13 章の内訳になる。**ブラウザ上で初めて動く振る舞い**
   (JS の絞り込み・表示切替)は、HTML に属性や埋め込みが存在することの試験だけでは
   確定にせず、人が動かして見るまで暫定にする。
5. **spec.html は派生物。** 手で編集しない。仕様が変わったら再生成する。
   古い spec.html と E2E が食い違ったら、正は常に E2E。
6. **仕様書の言葉で書く。** 聞き取りで利用者が使った言い方(「打つ」「知らせ」「もの」)を地の文に
   持ち込まない。データと状態に名前を付けて第 2 章で定義し、画面に出る文言・見出しは、かぎかっこで
   引用するときだけ画面のとおりに書く(`references/format.md` の「言葉づかい」)。
7. **実装の場所は書くが、説明は足さない。** 機能とエラーに関数の場所を書き、ビルドにソースを渡す。
   実在の確認・コードの抜粋・モジュール結合図の線・第 15 章は、ビルドがソースから作る。
8. **機能名・用語を変えたら旧語で原稿全体を grep する。** 章をまたいで旧語が残ると
   読者には別物に見える。旧語を残す場合は用語定義に旧語と新語の対応を載せる。

## 手順

1. `tests/e2e/` を読み、検証されている振る舞いを機能別に整理する。
   **各振る舞いを固定しているテスト関数名を控える**(検証欄に使う)
2. 実装を読み、**処理の実行順**と、**機能ごと・エラーごとの関数の場所**(ファイルと関数名)を把握する。
   機能の粒度は、利用者に提供する機能の単位にする(ユースケース・流れの工程と同じ大きさ。内側の
   細かい処理は機能にせず、その機能の `処理:` に書く)。**原稿は次の順で書く**:
   (1) 3.2 のユースケース(`@purpose`。利用者の目的で切り、誰が・対象・概要を書く)と、その流れ
       (`@flow`)の工程を、ID を添えずに並べる
   (2) その並び順に、工程の先頭の機能へ `F-01` から番号を振る
   (3) 番号を振った順に第 8 章の `@spec` を書く

   番号を先に振ってから流れを並べると、順序の判定で止まる。振り直しは `@spec`・3.2・
   各章の検証欄・エラー欄をまたぐので、流れが固まる前に番号を振らない
3. `docs/adr.md` を読み、決定と理由を対で要約する(全件でなく、利用者の理解に効くもの)
4. `docs/interviews/` の最新記録から「スコープ外」「保留」、**用語の対応**(利用者の言い方 → 仕様書の
   用語。第 2 章に載せる)、**外部インターフェースの要求パラメータ**(5.2 の `@param` に書く)、および
   **標準試験バッテリーの適用結果表**を拾う。「該当なし」で飛ばしたカテゴリがあれば、
   それが第 14 章の候補になる
5. `references/format.md` に従って `docs/.spec-src.md` を書く
6. ビルドする:

   ```bash
   python "${CLAUDE_SKILL_DIR}/scripts/spec_build.py" \
     --src docs/.spec-src.md --out docs/spec.html --code <ソースのフォルダ>
   ```

   `--code` には実装のあるフォルダ(`src` など)を渡す。原稿の `実装:`・`@impl` に書くファイル名は、
   このフォルダからの相対で書く。**ソースがあるなら必ず付ける**(付けないと、関数の実在の確認・
   コードの抜粋・参照の線・第 15 章が出ない)。調べられる言語は、フォルダにあるファイルの拡張子で
   決まる(Python・PowerShell・Bash を同梱。足し方は `references/analyzers.md`)。

   `${CLAUDE_SKILL_DIR}` はこのスキル自身のディレクトリに展開される(プラグインルート
   ではない)。展開されず文字列のまま残る環境では、`**/spec-digest/scripts/spec_build.py`
   を検索してそのパスを使う。
   「ソースにあって仕様に対応が無いものが N 件」の注意が出たら、第 15 章でその N 件を見る。
   仕様の書き漏れなら原稿に足し(環境変数なら 4.3 か 5 章、止まる箇所なら 9 章と `@impl`)、
   利用者が決めていないものなら第 14 章に載せて、どちらにしたかをユーザーに伝える
7. **失敗したら**、stderr の「N 行目: …」に従って原稿を直し、通るまで 6 を繰り返す。
   失敗時は既存の spec.html を書き換えないので、途中で壊れた仕様書が残ることはない
8. 「決定はあるが試験が無い記述が N 件あります」の注意が出たら、その N 件を確認する。
   本来は実装フェーズのバッテリー適用で見つかるべきもので、ここで出るのは前段の漏れ
9. **査読を受ける。** ビルドが通っただけでは、言葉づかい・機能の粒度・概要の書き方は確かめられて
   いない。`references/review.md` の手順で、経緯を知らない読み手(サブエージェント)に原稿と
   生成物を読ませ、指摘を直してビルドし直す。直さなかった指摘は理由を添えてユーザーに伝える。
   読み手を立てられない環境(自分がサブエージェントとして動いているときなど)では、
   `references/review.md` の観点で自分で読み直し、**読み手を立てられなかったことを報告に書く**。
   **用語と名称は、読み手に全件を採点させて決める**(ビルドに `--terms docs/.spec-terms.md` を付けると
   採点の対象が書き出される。基準と決め方は `references/term-scoring.md`)
10. 原稿 `docs/.spec-src.md` は残す(次回の再生成の下書きになる)。
   `.gitignore` に入れず、E2E と一緒に更新する
11. ユーザーには「`docs/spec.html` をブラウザで開いてください(処理の流れは別紙 `docs/spec-flow.html`。3.2 のユースケース図から開けます)」と伝え、
    表紙の件数(機能・エラー・非機能要件・E2E・確定・暫定)と、査読で直したこと・残したことを添える

## よくある詰まり

- **第 7 章・第 13 章を書いてしまう** — 原稿に書くとビルドが「章の番号・順序が違う」で
  止まる。この 2 章は自動生成
- **ID が連番でない** — 機能は 3.2 に並べた工程の順に `F-01` から。エラー・非機能要件
  なども各章で `01` から連番。抜けや飛びは止まる
- **機能 ID の順序で止まる** — 「機能 ID は 3.2 の各 @flow の中で、工程に添えた先頭の ID が
  小さい順に振ります…F-08 が F-16 より後に現れています」。原因はたいてい、番号を振ってから
  3.2 の流れを並べたこと。3.2 の工程の並びを正として `F-01` から振り直す(第 8 章の並びも合わせる)。
  保存のように複数の流れで使う機能は、使う工程の 2 つ目の ID として添える
- **`枝` の閉じ忘れ** — `枝` は分岐に入る側と本線に戻る側の 2 回書く。1 回だけだと止まる
- **機能が処理の流れに現れない** — 第 8 章の全機能が、3.2 のいずれかの工程に
  `| F-nn` として現れる必要がある。内部で実行される機能は、呼び出す工程に並べて書く
  (`| F-03 F-04`)

## 旧 `docs/spec.md` がある場合

v0.2 以前は Markdown で出力していた。同じ内容が二重に残るとどちらが正か分からなくなる。
`docs/spec.html` を生成したあと、**ユーザーに確認してから** `docs/spec.md` を削除し、
README などの参照を張り替える。

## 品質基準

- **可読性**: アプリを知らない人が spec.html だけで「何ができるか・どう使うか・
  何をするとどうなるか」を把握できる
- **整合性**: 第 8・9・10 章の検証欄のテスト名が実在するテスト関数と一致する
- **正直さ**: 人が確認していない振る舞いを「確定」にしない
- **保守できること**: 機能・エラーから実装の関数へ辿れる。ソースにだけある事実(環境変数・
  書き込みと削除・止まる箇所)が、仕様のどれに当たるか、または未確定かが分かる
- **仕様書の言葉**: 地の文がシステムの用語で書かれ、機能が利用者に提供する単位で数えられている
